# Repository Guidelines

## User privacy

Do not use the user's personal name in responses or add it to documentation, examples, test fixtures, comments, generated assets, or attribution. Use neutral wording and fictional sample names. Avoid recording identifying usernames or absolute home-directory paths in project files.

## Follow-ups

Read [TODO.md](TODO.md) at the start of a task and keep it updated when discussing or completing follow-ups. Organize outstanding work into Fixes, Enhancements, and Testing, without deferred/proposed categories or repeated approval labels; listing an item does not authorize implementation. A Fix is behaviour that is wrong; style and cleanup work is an Enhancement. Remove completed items.

## Project structure

Rust workspace. The root package builds the one `cuboid-wars` executable: `src/main.rs` parses the CLI and picks the mode from one optional flag (`--host`, `--join`, or `--serve`, each with an optional address; none is single-player), and `src/host.rs` runs the embedded server thread for the two modes that play and serve at once. Three library crates hold everything else:

- **`common/`** — shared between client and server.
  - `math.rs` — `direction_from_yaw_pitch`, `sequence_is_newer`, `PHYSICS_EPSILON`, and the glam ↔ Rapier conversions (`to_rapier`, `from_rapier`, `rapier_pose`) every physics file uses.
  - `protocol.rs` — all `ClientMessage` / `ServerMessage` variants and wire structs. Read the top-of-file doc comment before adding a new message — it lays out the bootstrap / state / cues / events roles and the two lanes that decide where new messages go. It re-exports `sequence_is_newer` for stream ordering.
  - `network.rs` — the wire definition on renet: three channels (reliable ordered, unreliable, and retransmitted-unordered for unreliable-lane messages larger than one packet, chosen by `channel_for`), the bincode codec, and the netcode protocol id. The header comment is the authority. Which lane a message rides is decided by its role in `protocol.rs` (`Lane`, `lane()`).
  - `physics/` — what both crates run: the shared character motor (`characters/`: `step_character_movement`, support and ladder rules, the velocity components, move-plan intersection), collision world (`world/`, one `impl CollisionWorld` per concern: construction, carrier poses, and bridge power in `collision_world.rs`, rays in `rays.rs`, ball casts in `ball_casts.rs`, ground probes in `ground.rs`, the character controller call and capsule sweeps in `character_queries.rs`, free-flight sweeps, overlap recovery, and carrier pushes in `flight.rs`, cached geometry bounds and revisions in `bounds.rs`, portal backing and host materials in `portal_backing.rs`, barrier instance filtering in `colliders.rs`, and the non-solid ladder climb volumes with their lookups in `ladders.rs`), barrier passability, the blast falloff rule (`blast.rs`), the stall watchdog (`watchdog.rs`), and portal geometry + traversal (`portals/` — aperture frames, placement/overlap validation, character/projectile hops, and the `PortalSet` the client rebuilds from the replicated portal list and the shared motor reads for corridors and funnels). Generic collision queries stay with `CollisionWorld` and its private collider state; navigation policy belongs to its caller. Other code only one crate runs lives in that crate: the owner's player step, bullet flight, and missile lock-on are the client's; actor steps, move-plan blocking, and health rules are the server's. Carriers are the one geometry that moves: `world/carrier_sync.rs` places their colliders each tick, and the character step carries whoever stands on one.
  - `types/` — shared markers, IDs, player body generations (`types/player_generation.rs`: `PlayerGeneration` with advancement and wrap-aware ordering), positions, movement states, map layout types (`types/map_layout.rs`), items/power-ups, snapshot entity records, feed spans (`types/feed.rs`), the texture settings and their validators (`types/textures.rs`), the shared clock (`types/tick.rs`: `ServerTick`, `server_tick_advance_system`), and the kind tables. `types/kind_table.rs` holds the generic `KindTable<K: KindId>` that both `BarrierKindTable` and `BridgeKindTable` alias, so one implementation carries the id↔string mapping, the optional max-kinds check, and the error wording for both catalogs. `types/plates.rs` holds `PlateState`, the single value naming everything the pressure plates currently hold: the active switches, the barrier instances they open, the bridge instances they power, and each switched carrier's run. `types/switches.rs` holds `SwitchId`, the `SwitchTable` alias, and `SwitchDef`, one entry of the root layout's `switch_kinds` catalog.
  - `map/` — shared map behaviour: ramp surfaces (`levels.rs`), carrier poses (`carriers.rs` — `CarrierPose`, `carrier_offset_at`, a pure function of a carrier's run ticks, `CarrierRun`, the replicated run of a switched carrier, and the `Carriers` runtime state both sides advance from the tick and the plate state), and grid↔carrier conversion (`geometry.rs`, `MapGeometry`, built from the grid size and the map's `MapGeometryConfig`). The per-map cell size, storey height, and floor and wall thicknesses ride `MapSettings.geometry` (`config/geometry.rs`, which derives the wall height, half wall thickness, barrier and bridge thicknesses, `level_y`, `level_for_y`, and `nearest_level_to_y` from them); the barrier and bridge thicknesses and the wall light height are fractions in `constants.rs`, and the only other fixed world sizes are the ladder rail geometry and the portal aperture, both in `constants.rs`. Layout records are in their carrier's frame (world space on the world carrier) — the server fills `y`/`height` on walls, barriers, ladders, and plates at compile time — so the physics and the client place them without the map's sizes and only grid logic needs `MapGeometry`.
  - `health.rs`, `constants.rs`, `config/` — the `Health` type, gameplay constants, and the shared configuration types; `config/network.rs` holds `NetworkConfig` (the `gameplay.json::network` rates) and `UpdateCadence`, the send-rate ticker both crates run.
- **`server/`** — authoritative headless server (Bevy `MinimalPlugins`).
  - `app.rs` builds the ECS app (`build_server_app`, with `ServerAppOptions` for the map, the rate overrides, and whether it installs the log plugin) and runs it (`run_server_loop`, paced by the runtime's timer on the calling thread); it installs function-style domain plugins, matching the client pattern, and each domain's `plugin.rs` owns its system registration. `schedule.rs` defines their cross-domain tick order (`Prepare` → ingress → behaviour/movement → combat damage/removal/explosions → lifecycle/maintenance → snapshot). Deferred commands are flushed after preparation, ingress, and combat, and again immediately before snapshots, so ID maps never expose unmaterialized entities to network collection.
  - `actors/`, `characters/`, `items/`, `players/`, `portals/`, `projectiles/`, `quests/` — server-side domain systems. `actors/movement/step.rs` is the actor step policy over the shared motor and `plan.rs` the move-plan blocking rules; `characters/geometry.rs` and `characters/health.rs` hold the server-only character helpers; `schedule.rs` also converts seconds to ticks (`ticks_from_secs`). Each domain keeps its Bevy resources in its own `resources.rs` (`players/resources.rs` separates `PlayerInfo` into connection, session, and per-life state inside `PlayerMap`, while `players/outcomes.rs` receives owner-reported contacts and landings; `quests/catalog.rs` holds immutable definitions/indexes, `quests/resources.rs` the mutable session-wide `QuestBoard`, and `quests/progress.rs` the `record_event` entry point). Actor AI uses separate contact/beam controllers over `Roam`/`Engage`/`Evade`/`ReturnHome` modes; actors configured as `immovable` stay at their carrier-local spawn anchor and have no per-map speed settings, and active beam bursts reselect exposed targets every tick (`actors/behavior/controllers.rs`, with the mode-entry transitions in `behavior/transitions.rs`); ground navigation (`actors/navigation/ground/`, one `NavGraph` per carrier grid in `NavGraphs`) routes across connected carriers; `navigation/home.rs` holds zone-based roaming territories over `server/src/map/volume.rs` and `navigation/air/` handles flying actors with incremental 3D searches, while `behavior/flight.rs` and `movement/flight.rs` own their decisions and movement.
  - `network/` — the whole networking concern. `links/` is the link layer: `resources.rs` (`LocalLink`, the server's ends of the host's own client's queues, registered at build time through `register_local`; `ClientLinks`, every player's `LinkSource`, a queue for that client or the listener's connection for a remote one), `transport.rs` (`listen` binds the netcode socket into the `Listener` resource, absent in single-player), and `outgoing.rs` (flushes every remote player's queued replies to renet in `Last`); a closed queue or a netcode disconnect is the player leaving, and `PlayerConnection::hang_up` closes a link from the server side. Above it, Bevy ingress (`incoming.rs` polls the listener, registers remote players on connect events, and drains every link) and authenticated client-message routing (`routing.rs`/`handlers.rs`), login, snapshot and configured-rate player/actor movement broadcasts (`snapshot.rs`/`broadcast.rs`), server-rendered feed lines (`feed.rs` — wording, styled spans, broadcast/private audience), and admin commands (`admin/handler.rs` owns authorization and replies, `admin/command.rs` the grammar and `/help`, and `admin/execute.rs` world mutation; world-affecting commands announce to everyone, the rest reply to the issuer).
  - `projectiles/` — immediate cosmetic volley relay (`spawn.rs`) and reliable shooter-reported damage (`hits.rs`), queued for the combat phase in `PendingProjectileHits`. The server keeps no bullet entities or flight state.
  - `missiles/` — launch acceptance (`spawn.rs`), owner movement/detonation reports (`reports.rs`), and the lifetime fallback (`expiry.rs`: a missile whose owner stops reporting is detonated at its last reported position once `missiles.lifetime_secs` plus a margin has passed). `MissileMap` holds the reported wire state and the launch tick; the server runs no missile flight, collision, or blast-hit detection.
  - `combat/` — damage application (`apply_damage`) + `kill_player`/`kill_actor` (`damage.rs`, the one-stop death sequence) and blast resolution (`explosions.rs`, with `PendingExplosions` in `resources.rs`; missile blasts carry shooter kill credit).
  - `map/` — converts map definitions into runtime layout: `definition/` loads, validates, and compiles the map documents (see “Nested maps”), then cells/edges, floors, walls, ramps, barriers, light bridges (`bridges.rs` merges same-kind cells into rectangles, largest first), lights, masks, segments; the runtime map model lives in `map/resources.rs` (with `MapFireworks`, the selected map's fireworks switch and cooldown), and `pressure_plates/` holds the plate system and its switches (see “Pressure plates”). Also the weather and day/night schedulers (`weather.rs` and `light_cycle.rs` — driven by `cycles.weather`/`cycles.lighting` and each map's `weather`/`lighting` mode, broadcast as `SSnapshot.rain_intensity`/`lighting`, overridable via `/weather` and `/light`).
  - `config/` — server config split by concern: gameplay loading/projection (`gameplay.rs`), map registry (`maps.rs`), and focused actor, combat, cycle, falling, item, missile, quest, respawn, scoring, feed, weapons, and validation modules.
  - Runs at `network.server_hz` (default 30) via the manual `app.update()` loop in `run_server_loop`; server `Time` advances one configured tick per update (`TimeUpdateStrategy::ManualDuration` in `app.rs`), so timers and carriers agree, and an overrun skips wall time instead of stretching a tick. Clients use the same fixed step from `SInit`. `server_hz`, `update_hz`, and `snapshot_hz` share the gameplay JSON network block and have matching hyphenated CLI overrides (`NetworkOverrides` in `app.rs`, filled from the executable's `WorldArgs`); movement and snapshot rates must not exceed the server rate.
- **`client/`** — Bevy renderer, input, UI.
  - `app.rs` builds the Bevy app around the two queues, loads and validates client config, installs shared resources, and registers domain plugins; `ClientAppOptions.logging` says whether it installs the log plugin, and the asset root is anchored at the client crate at compile time like its config paths, since the executable's package is the workspace root. CLI parsing and process lifecycle belong to the root package.
  - `network/` — `link/` is the link layer: `resources.rs` holds `ClientToServerChannel`, the shared send handle, and `ServerLink`, the app's side of the connection (the host's own client reads its server's queue, a joined client pumps the `RemoteLink` in `transport.rs`, which `connect` starts); `outgoing.rs` flushes the frame's sends in `Last` and tells the server on the exit frame; `impairment.rs` holds `DelayQueue` and the `--lag-ms` delay, `--jitter` variation (unreliable messages only, released by delivery deadline), and the `--drop` loss simulator (unreliable messages only, discarded before delivery). Above it, `incoming.rs` receives in the `Network` set, `bootstrap.rs` logs in (`login` sends `CLogin` and pumps the link until `SInit`), `resources.rs` holds `LastSnapshotTick` and `LastPlayerMovesTick`, the ordering guards on the two state streams, `tick.rs` holds `TickSync`, the pong-driven clock correction, and `ping.rs` owns the ping cadence and `apply_pong`, which measures every pong against the send time it echoes; `sample_buffer.rs` holds `SampleBuffer`, the one delayed-playback buffer remote players, actors, and missiles share (it steers its playback rate to keep the lead at `SampleTiming.delay_ticks`, re-centres after a stall, caps sequence gaps, and can be sealed to fly out to a final sample); `routing.rs` unwraps `ServerMessage` envelopes and calls focused domain handlers directly (`players/`, where `moves.rs` queues remote movement samples and `handlers.rs` owns the cues; `actors/`, `items/`, `missiles/`, `portals/`, and `projectiles.rs`, which spawns relayed volleys), all of which read the one `ServerMessageContext` in `context.rs`; `bootstrap.rs`, `quests.rs`, `snapshot.rs`, and `presentation.rs` own the remaining message handling.
  - `players/`, `actors/`, `characters/`, `items/`, `projectiles/`, `missiles/`, `bridges/` — client-side domain systems (`players/movement/interpolation.rs`, `actors/interpolation.rs`, and `missiles/interpolation.rs` blend buffered remote samples into the gameplay components each frame; `transform_sync.rs` files only place the rendered models; `characters/remote_pose.rs` resolves a rider's carrier-local sample at the rendered carrier pose; the single-clip actor animation observer lives in `characters/animation.rs`). `missiles/` holds the procedural mesh, crosshair lock-on (`lock_on.rs`), the clear-runway launch (`launch.rs`), flight state (`flight.rs`), shooter guidance (`guidance.rs`/`steering.rs`), swept movement and blast-hit reporting (`movement.rs`/`blast.rs`), and observer interpolation (`interpolation.rs`, which flies a sealed timeline to the reported impact before exploding). Its `air_graph.rs` routes through carrier-local air volumes supplied at bootstrap; `pathfind.rs` holds the BFS traversal, independently of server actor navigation. `missiles/lock.rs` holds the crosshair lock rule. `projectiles/` owns bullet flight end to end: `motion.rs` (velocity, gravity, drag, bounces, field impacts), `events.rs` (ranking one step's events), `hits.rs` with `characters/ball_hits.rs` (swept ball versus character hitboxes, shared with missiles), `spawning.rs` (volley geometry and the muzzle check), and the systems that present them. `players/movement/step.rs` is the owner's step policy over the shared motor and `state.rs` its wire ↔ component mapping; `portals/refresh.rs` re-places carried portals each tick. `bridges/` holds the double-sided light bridge surfaces: pane and frame materials per drawn surface (`assets.rs`, one per `bridge_visuals` group), clipped panes and outer frames (`surface.rs`/`spawn.rs`), and the alpha ease between the unpowered ghost and the powered surface (`fade.rs`).
  - `characters/model.rs` loads every character GLB once (`load_character_model`) and attaches the configured scene when the file has loaded; the ready observers take their clips from the loaded `Gltf`, and the comment there says why nothing requests a sub-asset by label.
  - `characters/inspection.rs` draws the B-cycled inspection views: Off, Grounding, and Hitbox. Debug shapes follow interpolated feet positions without model animation or hit shake; capsules stay upright and damage boxes follow gameplay facing. Grounding shows the movement capsule and adds the probe line, contact point/normal, and a billboarded Grounded/Airborne/Ladder label. Cycling views shows no HUD banner.
  - `cameras/` is the whole camera domain: `FollowCamera`/`CameraAim` state, the follow, rearview, and local-player-layer systems, and `camera_plugin`, which registers them and initialises the camera resources. `cameras/third_person.rs` follows an interpolated shoulder pivot with a Rapier sphere sweep, immediate obstruction retraction, and eased extension. V cycles the debug view, a free orbit around the character's centre entered at `camera.debug.distance`, wheel-zoomed without limit, through geometry, never locked: first with level focus, then with every storey shown, then back to the previous follow view; the wheel zooms between first and third person, entering first person by zoom enables facing lock (an obstruction that collapses the arm does not), F toggles third-person lock, and the mouse orbits in both states without holding a button; `input/camera.rs` owns the wheel zoom and the F toggle. The settings menu saves mouse and zoom sensitivity multipliers (default 1), with base speeds in `constants.rs` and logarithmic slider tracks. `camera.follow`, `camera.debug`, `camera.rearview`, and `camera.shake` hold JSON tuning; menu-controlled values live in `ClientSettings.preferences`, initialized from `constants.rs`. Follow zoom starts at zero; `camera.follow.first_person_distance` controls both the eye-position snap and body visibility after collision resolution, while preserving requested zoom around obstructions. Local mesh layers are assigned in PostUpdate after scene spawning and before visibility checks. The main follow view and rearview share the live FOV preference. `cameras/aim.rs` converges third-person shots from the player's eye onto the camera target; weapons and missile locks consume that same aim after camera sync, while movement owns body facing. `input/cursor.rs` owns cursor capture, separate from movement suspension and menus, and re-grabs the pointer at the window centre whenever the window gains focus, since macOS locks it only for the foreground app; its mouse-motion filter keeps recentering out of mouse-look; `input/focus.rs` clears held input and movement intent on window focus loss before physics runs.
  - `players/animation.rs` drives humanoid player clips from movement support and velocity (the owner's own step, a remote player's buffered samples): idle, walk/run, strafing, ladder climb/hold/descent, jump/fall/landing, and stun. While attached to a ladder, `input/movement.rs` keeps the player facing its rails independently of the view and climb direction. Platform motion and knockback do not drive footsteps. `client/assets/models/player.py` rebuilds the skinned GLB with embedded PBR textures; `player_mocap.py` retargets CMU captures from the adjacent `mocap/cmu/` directory, and `player_preview.py` renders a motion study. Footstep contacts in `players/footsteps.rs` follow the active clip, with separate reverse phases and four contacts per strafe loop; timings are in `constants.rs`. Ladder ascent and descent use the climb clip’s rung contacts and the ladder material’s sound, remaining silent while holding still. Material definitions may name a `footstep` sound set in `assets.json`; `footsteps.default` handles unassigned surfaces, while each set owns its original sample filenames, `volume_db`, and optional accent. `footsteps.volume_db` adjusts all steps in addition to each set’s level, and `footsteps.ladder_volume_db` adds a climbing adjustment to both the main sound and accent; the saved `preferences.footstep_volume_db` adds the menu adjustment. Remote steps use positional audio. Each player alternates odd and even zero-based sample-list indexes across steps, including accents and ladder contacts; a one-sample list serves both feet. `world/surface_materials.rs` shares the collision-face material lookup with portal placement.
  - `actors/aim_rig.rs` binds configured `model.aim_rig` yaw/pitch/muzzle nodes when a scene loads; `vfx/laser.rs` aims them along the visible beam and anchors it at the muzzle. A rig's pitch node must sit at the yaw node's origin with the muzzle as its direct child and its axis on local −Z; `aim_rig_setup_system` rejects any other wiring. `model.rotate_with_facing` controls whether the body follows gameplay facing; the turret keeps its pedestal heading. Its hitbox fits the pedestal and main head, excluding the barrel; the actor's optional `beam_origin_height` keeps beam clearance and damage at the gun head independently of the body's centre. `client/assets/models/turret.py` rebuilds the textured GLB in Blender; `-- --preview` renders a still.

  - `client/assets/models/zapper.py` builds the hovering drone with an embedded plastic-shell atlas over plain metal and animated lift fans and stabilizers. The gun inherits the hull's hover while the shared aim rig reads its animated parent transforms after animation evaluation to keep the beam anchored; `-- --preview --motion` renders stills and a motion study. Moving character models face glTF +Z (Blender -Y); aim joints use local -Z for the muzzle axis.
  - `items/symbols.rs` builds extruded pickup meshes, sphere clusters, and HUD masks from `client/assets/symbols/items.json`; the map editor reads the same outlines. Pickup materials share `vfx.pickups.emissive_brightness` from `config/client/client.json`, including keys and missile pickups; in-flight missiles keep their own materials. Gold pickups render as beveled gold coins with raised stars (`items/coins.rs`); health pickups use a green cross. All pickups share the same floating height, bobbing, and Y-axis spin. Pickup materials are untextured.
  - `input/`, `cameras/`, `ui/`, `vfx/` — client-only interaction, rendering support, presentation. The explosion effect is one subsystem in `vfx/explosion/` (assets, spawn, animation, scorch, shards, smoke); its scorch marks and shockwave ring hang under the carrier root of the surface they hit, in that carrier's frame like the map record they mark, and a grass burn matches grass on its own carrier only and burns only where the ground mark shows; a mark is cut to the surface it lies on, the coplanar floors, wall tops, or ramps around a ground contact or the wall's rectangle, minus the shadow the blast throws past every wall, floor, and ramp within reach, so it neither floats past an edge nor shows through a wall, a floor, or a ramp (`vfx/explosion/scorch/`: the placements, the polygon clip, and the ring variants); `vfx/` also holds the zapper laser beam (`laser.rs`, spawn/despawn from the snapshot's bursts and per-frame aiming in one file), rain (`rain.rs`), missile exhaust (`exhaust.rs`), the shared GPU particle clouds (`particles.rs` — every particle in the game is a cube; keep new effects spark-sized or they read as floating boxes), the translucent kind-material recipe and exponential ease shared by barriers and bridges (`fade.rs`), and the seeded client-side firework show (`firework.rs`, played on `SFirework`; the fireworks switch spaces its shows by the shared `FIREWORK_SHOW_SECS` plus the map's cooldown, so only `/firework` can arrive mid-show, and the show still playing wins). The Esc-toggled settings overlay (`ui/settings_menu/`) edits live state — window mode/vsync on the `Window`, the rest on `ClientSettings.preferences`/`GlobalVolume` — using Bevy's headless `bevy::ui_widgets` behaviors under game-styled wrappers. Master, footstep, and Enemy movement volume sliders use dB with a neutral default of 0 and a range of −20 to +20; the left endpoint is Off, converted to zero gain by `audio/volume.rs`. Pending settings changes save to `config/client/client_local.json` once edits have stopped for 500 ms, on closing the panel, and before normal window close or `AppExit`; Ctrl+C remains an immediate exit. The last windowed position and logical size are restored by `WindowedFrame` in `input/window_frame.rs`: macOS uses points, Windows/X11 use physical desktop coordinates, and Wayland leaves placement to the compositor. A windowed start stays hidden until placed, since a restored position lands one frame late (the comment there says why), and the shown window requests focus once, for a macOS launch that lands behind the terminal. The fullscreen shortcuts also work with the settings menu open. The chat + admin console (Enter or `/`, ↑/↓ history) lives in `ui/console.rs`; its editor emits a typed submission and a separate adapter sends `CChat` or `CAdmin`. The message feed (`ui/message_feed.rs`) only maps server-authored `SFeed` spans to client colors. Banner timing in `client.json::hud.banner` has per-purpose `duration_secs` (including fade) and `fade_out_secs`; message-feed rows retain their shared fade duration. The feed and typed/config-driven HUD banner (`ui/hud_banner.rs`) are timed-line stacks (`ui/timed_lines.rs`: rows that live, fade, and go); the console prompt is the last row of the feed column.

Other notable paths:

- `tools/editor.py` — launcher for the PySide6 map editor (code lives in `tools/map_editor/`); takes a map name and edits `config/server/maps/<name>/layout.json`.
- `client/assets/` — 3D models, textures, audio. Keep asset generation scripts beside the assets they generate. `python3 client/assets/sounds/analyze_audio.py` measures every game audio asset into `sounds/analysis.json`; `--check` verifies the saved results. It retains file hashes, duration, peak and RMS measurements, plus gain toward a common strongest-50-ms RMS target with sample-peak headroom. `client/src/audio/normalization.rs` applies the correction once when any `AudioPlayer` is added, including loops. Named player and actor sounds in `assets.json` each own a `file` and optional `volume_db` (default 0); `audio/playback.rs` applies that adjustment independently of other sounds using the same file. Actor `fire` sounds are optional; only firing actors need a binding. The `actors` block holds its named definitions under `kinds` and owns `movement_volume_db` and `sfx_volume_db`, added to the per-sound levels for movement loops and actor explosions, beams, and hit effects respectively. Optional actor `movement` sounds loop at the actor’s position (`actors/movement_audio.rs`), with pitch and gain following travel speed, smooth starts/stops, and a quieter idle for flying actors. The Enemy movement slider saves `preferences.actor_movement_volume_db` and adjusts live loops in addition to the JSON levels; its Off position mutes them. `audio/looping.rs` shares decoded samples with independent playback cursors, keeping output channels aligned through spatial mixing. `client/assets/sounds/actor-movement.py` synthesizes the light/heavy tank and quadcopter loops. Footsteps use their existing set and accent adjustments. The rain envelope retains both its sound adjustment and file normalization.
- Model textures should add visible coarse relief or be authored for the specific model. Use plain materials for subtle paint and metal. FreePBR synthetic rubber (`synth-rubber`) is an approved external texture for tires and finer player elastomer; discuss any other third-party texture use first. Preserve generators for authored textures and record provenance.
- Keep `client/assets/ASSETS.md` as simple asset/source/license lookup tables. Use `TBD` for unknowns; omit local source paths, search reports, and explanatory narratives.
- `client/assets/ASSETS.md` — asset provenance register. Update it when adding or replacing assets, including embedded textures and animation sources; retain supplied license notices and ask about unknown origins.
- `config/client/assets.json` — hand-edited asset set (materials, alias bindings, models, sounds, wall-light variants, skyboxes with their celestial disc, and the ladder and pressure-plate fixture bindings).
- `config/client/client_local.json` — local values from the settings menu, the fullscreen shortcuts, and the last windowed placement. Gitignored, so `git pull` cannot update it: unlike every other JSON it carries a version, and any format change must bump `LOCAL_SETTINGS_VERSION` (`client/src/config/local.rs`) — a stale version is discarded and rewritten, never migrated.
- `config/server/gameplay.json` — the global gameplay configuration. Its `network` block configures `server_hz`, `update_hz`, and `snapshot_hz` (the two rates between 1 and `server_hz`), overridable with server `--server-hz`, `--update-hz`, and `--snapshot-hz`; the effective values ship in `SInit.world.network`. It holds player and per-kind actor bodies; shared projectile, missile-lock, missile-guidance, and portal tuning; server-only actor behaviour, combat, scoring, feeds, and weather/lighting cycles; and the named-map registry. The multi-shot `patterns` block is a palette; `allowed_patterns` names the ordered subset that ships and that Q cycles. `maps` is an explicit array of registered map names. The loader resolves every map’s `settings.json` into `ServerGameplayConfig.maps` and validates it against global tuning, naming the source file and field in errors; the root layout's `switch_kinds` and `fireworks` are read and validated when the selected map is generated (`generate_map` fills `MapSettings.switches` and returns the switch table and the fireworks switch). Each map’s `config/server/maps/<name>/settings.json` owns its `geometry` block (`grid_cell_size`, `level_height`, `floor_thickness`, `wall_thickness`), its complete `movement` block (gravity, player walk/run/jump and actor/projectile/missile speeds, ladder climb ratio, knockback), portal ownership (`portals`: `single`/`both`), `textures` (alias → explicit `portalable` boolean), `barrier_kinds` and `bridge_kinds` (ordered catalogs of `id` and `color`, also determining matching key names and colors for barriers, shipped to the client), optional `random_items` (`weights` maps item ids to finite non-negative relative weights, with at least one positive; zero or omission disables an item; `max_number` is refilled each tick as free eligible cells allow, and `despawn_secs` retires uncollected items for immediate replacement), power-up durations in `power_ups.duration_secs` (`0` lasts until death or erasure), placed-item respawn times in `placed_items`, player/actor respawn policies in `respawn`, player fall-damage thresholds in `player_fall`, quests, skybox, weather, and lighting. A quest's points live beside that quest, and quest ids need only be unique within their map. `default_map` selects the map unless `--map <name>` overrides it. The server validates everything once and sends a client-only gameplay projection plus the selected map, the plates' current state, and the quest-locked switches through `SInit`; clients do not load gameplay JSON. Actor movement tuning and the kind's body (`ActorCharacter`) are resolved once into each server actor's components rather than looked up by kind during movement.
- `config/server/maps/` — one folder per named map, with `settings.json` for tuning and `layout.json` for geometry, zones, placed `items`, per-cell `light_bridges`, top-level `nested_maps` placements, embedded `nested_geometry` definitions, and `pressure_plates` — each naming the `switch` it operates; `actor_spawn_zones` carry their `respawn_secs` (`null` never refills) and may name a `switch` too. The root layout owns `switch_kinds`, target assignments, and optional `fireworks`; appearance kinds and tuning come from the sibling settings file.
- `launch_players.sh` — spawns a local multiplayer session of N tiled windows, the first hosting on 127.0.0.1:8080 and the rest joining it with the given impairment (`./launch_players.sh [num_players] [lag_ms] [drop] [jitter]`, macOS).
- `bacon.toml` — `bacon` job definitions; use `bacon clippy`, `bacon test`, etc. as the watch loop.

## Architecture notes

**Server is authoritative for**: player spawns and forced relocations, actor positions, gameplay outcomes, items, actor behaviour, reported bullet and missile damage, scoring, death/respawn timing, map generation (sent once on connect via `SInit`).

**Client owns**: input and final local movement, its own player's portal crossings, rendering, camera, UI, the death overlay. The server adopts every fresh, finite movement report for the current body, including velocities, momentum, knockback, and support. It retains each report in its carrier frame, resolves riders against the current carrier pose, and runs no player physics; ordinary server updates never reposition the living owner. The owner reports landings, crushing, void falls, and erasure commands reliably, and applies reliable additive blast impulses to its current motion. Respawns and forced relocations advance the body generation and arrive reliably through `SPlayerRelocated`, with snapshots as a fallback.

### ECS system ownership and cadence

Prefer handling discrete state at its change boundary when that keeps the code simple: ingress/lifecycle handlers own network-driven entity state, mode transitions own their presentation state, queries filtered with `Added<T>` handle entities created after initial setup, `Changed<T>` propagates component changes, and asset events drive post-load asset work. Small bounded scans are fine—especially for the game's small player, actor, and item collections—and are better than duplicated indexes, caches, or synchronization invariants. Guard equal writes only when they would wake a concrete change-detection consumer or renderer/UI propagation; a nearby comment should name that consequence.

Each output component has one semantic owner. If visibility or another final value combines multiple inputs, one system computes the complete value; independent systems must not overwrite one another in a scheduled race. Zero-data ECS tags use the `...Marker` suffix. Before adding maintenance bookkeeping, compare its complexity and consistency cost with the bounded work it avoids; optimize only when the simpler scan is meaningfully expensive.

### Message dispatch

Both server and client dispatch decoded wire payloads straight from ingress to one domain handler (`server/src/network/routing.rs`, `client/src/network/routing.rs`). Do not re-emit them as Bevy events: ingress is already a Bevy system with world access and each message has exactly one consumer, so an event layer adds no fan-out, scheduling, or parallelism — it has been tried, and it only obscured the receive-to-handler control flow. Reintroduce events only for a message that gains genuinely independent consumers. Bootstrap happens before the gameplay app runs: the executable sends `CLogin` and waits for `SInit` (`client::network::login`), then builds and validates the app from it; the server spawns the body at login unless placement is blocked or a group respawn is pending. The bootstrap rule that makes this safe without a readiness handshake is in the `protocol.rs` header. Once active, the server drops body-bound messages from a dead player, while `CPing`/`CAdmin`/`CChat` and reports for their in-flight missiles keep working through respawn.

### Protocol model

The message roles (bootstrap, state, cues, events) and the two lanes are defined in the top-of-file comment in `common/src/protocol.rs`; keep the detailed rules there only. Read it before adding a message. Most “X changed” state belongs in `SSnapshot`; a cue only for sub-tick latency, an edge-triggered side effect, or information a snapshot cannot carry; an event only when the snapshot cannot stand in for it.

### Gameplay systems

Actor kinds and their assets are configuration data. Runtime systems must select reusable capabilities from configuration, never hard-code actor names, asset paths, or model node names. Player-specific model handling is allowed only when necessary.

#### Death & respawn

`kill_player` in `server/src/combat/damage.rs` is the single death entry point; its function comment is authoritative for the sequence and callers. It does all death scoring: the victim pays `scoring.player_death` and a credited killer earns `scoring.player_kill`, once per death whatever the source; teammates pulled into a group respawn pay nothing. `explosions_system` drains player and actor blasts to a fixed point; death-blast kills award no kill credit (missile blasts do). `PlayerMap` owns the selected map’s `respawn` policy, individual and group player countdowns, and independent actor-reset countdowns that survive disconnects. Deaths and logged-in departures determine actor and switch reset eligibility from membership immediately before the event and living players remaining afterward; `never`, `solo` (sole logged-in player dies or leaves), `any` (any death or departure), and `all` (nobody alive remains, including group resets) share `common/src/config/death.rs`. Logout applies world reset policies without starting a group player countdown. `respawn.players` selects `individual` or `group`; `players/group_respawn.rs` puts surviving teammates and joining players into the shared countdown without extra kill credit, blasts, or death feed lines. `SPlayerDeath.effect` distinguishes explosions, void falls, and the silent group-respawn presentation. `players_respawn_system` restores bodies at saved checkpoints or spawn zones; its comment owns actor-reset timing and the in-flight-shot rule.

Checkpoints are rectangular `checkpoints` zones with a required `type`: `individual` saves the entrant's destination, `group_any` saves everyone's when one player enters, and `group_all` waits for visits from every logged-in player, including dead players. `players/checkpoints.rs` detects grounded entry after combat; spawn and respawn inside a zone do not activate it. Individual saves apply before one shared activation per tick, chosen in compiled map order; whoever entered another shared checkpoint that tick enters it again on the next, and re-entering the active shared checkpoint changes nothing. Visits survive death; joining adds a required visitor, departure removes one, and shared activation clears incomplete visits. `PlayerSession.checkpoint` survives death and clears on disconnect; `PlayerMap.shared_checkpoint` supplies later joiners until the last logged-in player leaves. Login and respawn share `players/spawning.rs` and respect group countdowns; a respawn retries a blocked checkpoint every tick, while a login places the joiner in a spawn zone instead (`spawn_zone_destination`) and keeps the checkpoint saved. A dead player's countdown holds at zero while blocked, and a logout then owes the full actor-reset delay. The private `SCheckpointReached` cue rides the reliable lane and plays the configured sound and short banner only when a player's destination changes. `fields/checkpoints.rs` draws an amber perimeter at half player height using the eraser materials; every checkpoint has the same appearance.

#### Barriers & keys

Barriers share one Rapier collision group, with query predicates filtering individual `BarrierId`s (`common/src/physics/world/colliders.rs`). The id table comes from the selected map's ordered `barrier_kinds` in `settings.json`, is built once at server and client startup, and reaches the client inside `SInit.world.map.settings`; each placed barrier's optional `switch` names its pressure plate kind, while every barrier accepts its matching key. Players hold a sorted `Vec<BarrierKindId>` in `PlayerInfo.life.held_keys`; the character filter excludes every barrier instance of a held key's kind, together with instances opened by pressure plates. Barriers are authored per level and grid edge; a barrier directly above a barrier with matching appearance and controls and no floor slab beside the edge between them compiles into one record spanning both storeys (`server/src/map/barriers.rs`), and `Barrier.levels` carries that span so the client's level focus keeps it visible on every storey it covers. Defined in `common/src/physics/world/colliders.rs` and `common/src/types/barrier_kind.rs`. Closed barriers and powered bridges block attack paths while remaining transparent to awareness (`attack_path_clear` and `attack_surface_along_ray` in `world/rays.rs`). Both absorb ordinary projectiles; missiles collide and their blasts respect the same cover. The client draws barriers, erasers, and light bridges through `client/src/fields/`: one shared `FieldMeshes` resource, a `KindVisual` (pane, frame, colour, and optional key material) per barrier kind or compiled bridge, merged double-sided panes, and 3D frames clipped against walls and floors on the same carrier. Both merge collinear neighbors and stack across floorless storeys; only barrier panes pulsate. Collision shapes remain cuboids, while keys use solid key-shaped meshes in their barrier kind’s color. The HUD derives its equipment slots from the map’s placed and random pickups (`SInit.world.map.items`, from `MapConfig::available_items`); key slots follow only the placed key kinds, not the barrier catalog.

#### Equipment erasers

Walk-through fields authored as per-level `erasers` grid edges, compiled to full-storey carrier-local `Eraser` records. Their separate volumes in `common/src/physics/world/erasers.rs` detect swept player contact and block portal shots; actors, projectiles, and missiles pass through. The owning client sends the `EraseEquipment` outcome when its step enters an eraser and then at the movement update cadence while it stays in contact, stopping its sweep at the entrance for portal crossings and checking the exit separately. `server/src/players/equipment.rs` applies the command after item collection, so erasure wins over a same-tick pickup. It keeps no eraser occupancy state. Erasers, pickups, and ladders are hand-tested volumes rather than Rapier sensors: sensors would need the collision pipeline for enter/leave events and still the swept test for fast crossings and moving fields, so they would not shrink the code. It clears power-ups and missile ammo, preserving keys, health, score, and quests. `SEquipmentErased` plays the affected player’s sound whenever equipment is removed, including fresh pickups while standing in a field. Power-ups use `PowerUpState::{Inactive, Timed, Permanent}` (`players/power_ups.rs`); an already-permanent pickup stays in the world.

#### Light bridges

Switch-powered walkways: translucent surfaces that are a faint ghost by default and turn solid and lit while their assigned pressure plate kind matches their On/Off response. Kinds and their colours come from the selected map's `bridge_kinds` in `settings.json` (`[]` when the map has none, like `barrier_kinds`). Authored per cell in the map editor and merged largest-rectangle-first at compile time (`server/src/map/bridges.rs`, which says why); `bridge_bounds.rs` fits full-width slabs flush against floors and neighboring bridges. The client draws double-sided panes at the walking surface and 3D frames around each controlled surface’s outline (`client/src/bridges/surface.rs`), sharing meshes and materials with barriers and erasers in `client/src/fields/`. Rectangle outlines and wall/floor clipping live in `client/src/fields/surface.rs`; joins with matching appearance and controls have no internal frame, and frames stay inside bridge footprints so adjacent kinds do not overlap. Only the panes fade with power; the collision slab keeps its full footprint. Bridge power is world state: every bridge shares one collision group that a collider joins only while its bridge instance is powered, applied from `PlateState` by the shared `powered_bridges_sync_system` on both sides, so no query carries the powered set; which queries see bridges and which stay bridge-blind is stated at `world_collision_groups` in `common/src/physics/world/colliders.rs`. Bridges set no floor flags, so item and spawn cells never see them, and missile routing checks the powered bridge colliders; each bridge cell carries its slab's `Cell.bridge`, which actor navigation walks while the plates power it: `nav_bridges_sync_system` applies `PlateState` to the `NavGraphs` before behaviour each tick, an actor whose next step lands on a bridge that lost power drops its route (`drop_route_onto_lost_bridge` in `actors/behavior/tick.rs`).

#### Pressure plates

Physical switches are pressure plates. The root `layout.json::switch_kinds` catalog gives each kind its shared policy; any number of plates can operate that kind. Each placed barrier, bridge, actor spawn zone, and moving nested map optionally names one kind in `switch` and selects On or Off with `switch_inverted`; the map-wide `fireworks` show names its kind alone. Appearance comes separately from `settings.json::barrier_kinds` and `bridge_kinds`. Every barrier accepts its matching kind's key automatically: a key grants its holder passage, while pressure plates open the barrier for everyone. Without a pressure plate assignment, barriers stay closed, bridges unpowered, actor zones active, and carriers running; fireworks need an assignment. A fireworks entry has no On/Off response and is rejected with one; the root `MapDef` denies unknown keys, and nested geometry may not define `switch_kinds`, `fireworks`, or `nested_geometry`. Compiled barriers and bridges have individual IDs for collision and rendering; only records with matching appearance and controls merge.

Map definitions allow one pressure plate per cell on each level. The occupancy and edge rules live with `pressure_plates_system` in `server/src/map/pressure_plates/system.rs`; the sibling `switches.rs` owns the runtime state and `PlateState` projection; `SInit.plates` seeds the client before its first snapshot. Each pressure plate kind configures `activation` (`momentary`, `toggle`, `auto`), `reset_on_player_death` (`never`, `solo`, `any`, `all`), and `held` (`any`: one occupied plate holds it; `everyone`: every living player stands on one of its plates, or every plate is held when players outnumber them). Auto toggles with exactly one logged-in player and is momentary otherwise; dead players still count. Toggle flips on each fresh plate press under `any` and on the hold rule's rising edge under `everyone`. Death and logout resets clear toggle state after combat and group transitions, with state and bridge colliders synchronized before player respawn. A held plate must release before pressing again after a reset. Every change of a switch goes through `PressureSwitch::set_active`, which flips its carriers' runs with it. Targets must name a known pressure plate kind operated by a plate in the placed map tree. While the fireworks target responds a show starts whenever the previous show (`FIREWORK_SHOW_SECS`) plus the cooldown has passed, each recording one `FireworksStarted` quest event; `/firework` records none. The plates of the fireworks switch are inert and hidden on clients (`SSnapshot.locked_switches`) while a fireworks quest is locked. The client loads `assets.json::pressure_plate.scene` and samples its `Activate` animation from `PlateState.active_switches`: active plates lower their tread, uncover rim lights, and show I on all four sides; inactive plates show O. Tread colors inherit the first linked barrier kind, then bridge kind, in catalog order; a switch's optional `plate_color` (`#rrggbb`) overrides that choice for other uses or mixed-color targets, with `pressure_plate.default_color` as the fallback. The editor uses the same colors. `pressure_plate.light_color` and `emissive_luminance` tune the lights; the half-cell footprint scales horizontally while the model's height and press travel remain fixed. The plate chain runs after `server_tick_advance_system` so a flip stamps the tick the carriers advance to.

#### Quests

The selected map's `quests` list is loaded into immutable `QuestCatalog`; `QuestBoard` holds only mutable session state. On login, the server assigns every currently unlocked quest and sends one batched `SQuestUpdates`; later assignments, progress, and completions use that same message with an explicit reason. Every update repeats the quest's complete client-visible definition, authored order, and current player/group state, so the client needs no catalog or earlier quest message; monotonic merging prevents stale progress or completion from regressing state. Group state also self-heals through `SSnapshot.quests`. Each quest has a `kind` (what advances it), a `scope`, points, and optionally `requires`. Scopes: `individual` (own progress on typed `PlayerInfo.session.quest_states`, own completion), `shared` (one pooled counter on the board; any player's event advances it; completes once for the group), `everyone` (own progress per player; completes for the group once every active player reached the threshold — the HUD shows `done/players`). `requires` hides a quest until the named `shared`/`everyone` quest completes; then it is assigned to every active player and to later joiners. Group completion is idempotent, normalizes shared progress to the threshold, credits every active player with that quest's points once, and reaches every active client as a completed quest update. `quests::record_event` is the entry point for gold, actor kills, and the firework launch; `quests::recheck_everyone_quests` re-checks `everyone` quests on disconnect. Kinds advanced by a world event rather than a player (`fireworks`) must be `shared`; a kind may claim the fireworks switch that solves it (`QuestKind::locks_fireworks_switch`), which keeps that switch's plates locked until the quest unlocks. `/quest` lists the selected map's catalog and `/quest <id> [name|@a]` completes one by fiat (`quests::complete_quest`, after `unlock_quest` if it is still locked).

#### Character movement

Shared `step_character_movement` takes a `CharacterStep` that separates `control_velocity` from `external_displacement`. Ladder interaction reads only control velocity; knockback rides external displacement so it can move a body without initiating or accelerating a climb. `step_player_movement` (`client/src/players/movement/step.rs`) applies the owner's gravity, barrier passability, knockback, and airborne momentum; `step_actor_movement` (`server/src/actors/movement/step.rs`) is the actor counterpart, with plate-opened barrier instances only and no portals. The client's fixed-step schedule (`local_simulation_plugin`) is the owner's simulation, not a prediction: nothing corrects it, a dead local body stops stepping and keeps its last position, and only a new body generation moves it. `client/src/players/movement/reports.rs` sends the owner's full state at `network.update_hz` in the frame of the carrier the motor rode (`CharacterMovementResult.carrier`, carried on `LocalMovementStep`), with immediate reports on portal crossings and carrier changes. `server/src/players/movement_reports.rs` keeps the newest report whole in `PlayerLife.movement`, in its carrier frame, rejecting unknown carriers; `players/movement.rs` resolves its world position before actor movement and gameplay consequences, and the broadcasts relay the retained report as received. Server player entities carry only position, facing, and health; the server and observing clients treat players as stationary reported bodies for character collisions, and neither runs remote player physics.

Observers play remote bodies through the shared `SampleBuffer` (`client/src/network/sample_buffer.rs`), `client.json::interpolation.buffer_intervals` update intervals behind the newest sample (2 by default: 200 ms at 10 Hz, about 67 ms at 30 Hz). The buffer keeps that lead by steering its playback rate, so a stall or a latency shift does not change it for good; it holds the newest sample when it runs dry, and remote players cut at portal boundaries. Riders report carrier-local positions, which observers resolve against the same rendered carrier pose as the platform; snapshots preserve that frame for joining observers, and the server sends each client the movement batch without that client's own entry. `TickSync` uses pongs; remote playback is timed by sender steps, and only riders move with a clock correction, through `Carriers`. Actors use the same buffer for carrier-relative server samples in `SActorMoves`; snapshots also feed the actor buffer, with one tick guard across both sources, while remote players are fed by `SPlayerMoves` alone. Actors keep their AI, physics, and outcomes on the server; clients treat their interpolated bodies as stationary obstacles and derive wheel speed from buffered travel. Only the shooter simulates missile flight; observers interpolate owner samples with the same buffer.

`client/src/players/movement/outcomes.rs` reports the owner's landing impact speed, crushing, falls out of the world, and eraser contact as `CMoveOutcome` events; `server/src/players/outcomes.rs` receives them, and the server applies damage and equipment rules. Eraser sweeps stop at portal entrances and also test the exit. Blast impulses add to the owner's current motion; only actor knockback decays on the server. `players/sync.rs` places each body generation once, whether its snapshot or reliable relocation arrives first, and resets the remote movement buffer; on the server every placement (login, respawn, the invincible void rescue) goes through `place_player_body` in `players/spawning.rs`, the rescue at the saved checkpoint like a respawn. `PlayerMap` remembers retired generations so delayed snapshots and body cues cannot revive them, even after the body is removed. A dead owner keeps its own death position; `SPlayerDeath.pos` serves observers' effects. Bullet volleys use unreliable cues and shooter-reported hits use reliable events; a jump is movement state in the next report.

Characters configure independent `movement_collider` (capsule diameter and total height) and `hitbox` (width, height, depth, and bottom offset). Positions and model offsets are feet-based; only a small contact margin separates the movement capsule from the floor. `common/src/physics/characters/support.rs` owns capsule support queries, carrier selection, and ground following after movement; Rapier handles stepping and slope sliding. `world/character_queries.rs` holds the character controller call and stabilizes character cast contact normals before the controller uses them. Stable edge overhang is allowed. Each step derives `CharacterSupport::{Airborne, Ground, Ladder}`; the server keeps the reported result inside the retained report for actor awareness, checkpoints, and movement broadcasts. Ground impacts retain the downward speed before collision clears it; ladder catches have no ground impact. Fall damage converts that speed to an equivalent normal-gravity drop for the map’s distance thresholds. The server sends the owner one landing cue: `SPlayerSoftLanding` plays `player.sounds.landing` without damage or shake; `SPlayerFallDamage` plays `fall_damage` with the health update and shake. The motor never reads this support back. Characters are not Rapier colliders: movement and projectile scans iterate the small player and actor lists with swept capsule tests, and contact attacks measure capsule surface distance with a closed formula (`server/src/characters/geometry.rs`). Registering characters in the broad phase was weighed and rejected at these counts (movement ordering, self-exclusion, and a second collider set to keep in step on the client), as were Parry contact queries while every movement shape is an upright capsule.

#### Bullets

Every client simulates visible bullet flight, ricochets, portal crossings, and the character hit its own view detects; only the shooter reports character hits. `client/src/input/weapons.rs` owns weapon selection; the bullet/portal cooldown is `LocalPlayerInfo.last_shot_time`, applied by `input/shooting.rs` and `input/portals.rs`. Shots use the current `CameraAim.origin`, and numeric multishot patterns follow the ordered allowed catalog. The shooter's muzzle check (`MuzzleCheck::Enforced` in `calculate_projectile_spawns`) decides the volley once; observers spawn the relayed volley without repeating it. Firework embers carry `EmberMarker` and never report damage. Shot delivery and in-flight lifecycle rules live in `common/src/protocol.rs`.

#### Missiles

Ammo comes from `missile_pack` items (capped by `missiles.max_missiles`; a full player leaves the pack in the world, like an already-held key or a potion at full health — `pickup_has_effect` in `items/collection.rs`; reset on death or erasure). Picking up a missile pack or using `/give missiles` selects missiles automatically; Q offers them only while ammo remains, and the last shot falls back to another held weapon. Left click fires; the client crosshair locks any player/actor near the aim ray (`acquire_lock` in `common/src/physics/lock.rs`, with a configurable assist radius). There is no cooldown, so ammo is the rate limit; with `missiles.require_lock` off, an unlocked shot launches unguided along the aim (the shipped config requires a lock). All feedback (sound + the missile) waits for the server's `SMissileLaunch` so a rejected shot never orphans a cue; only the HUD ammo count drops at once.

The shooter owns the whole flight: launch at a random spread angle (with a clear-runway resample), collision-checked lead pursuit + cosmetic weave while sight is clear, `AirGraph` BFS waypoints revalidated against moving geometry when blocked (a route whose waypoints all become unreachable replans on the next tick), turn-radius-aware obstacle checks, a swept proximity fuse that also needs a clear blast line to the target, and reliable reports of the detonation point and detected blast victims; the shooter plays its own blast at the impact point when it reports. A target the missile's radius cannot reach (one hugging a wall) is approached to a point inside fuse range with a clear blast line instead (`terminal_approach` in `steering.rs`), and a cached route is revalidated against that approach too — missile blasts are the only blasts that credit a killer. The fuse and the terminal approach sweep the missile's travel only (`projectile_sweep_clear`), so a missile skimming a floor or door frame still fuses; one swept inside geometry by a carrier detonates where it is. Missiles do not traverse portals: one chasing a target through an aperture detonates on its backing. A missile that stops making progress self-detonates (`stall_secs`, via the shared `ProgressWatchdog`). The server applies reported falloff and impulse directions with its damage/knockback tuning (`common::physics::blast_hit` is the one falloff-and-shove rule both sides use), checks victim generations, resolves resulting deaths and chain explosions, and detonates a missile whose owner stops reporting (`missiles/expiry.rs`). Missile protocol ordering and lifecycle rules live in `common/src/protocol.rs`.

#### Portals

Q cycles the weapons the player owns; projectile access comes only from the separate `single_shot` and `multi_shot` pickups, missiles require ammo, and portals require the `portal_gun` power-up. Weapon pickups select their mode on collection, except single-shot preserves an active multishot selection. Automatic fallback prefers the first multishot pattern, single-shot, missiles, then portals (`client/src/input/weapons.rs` keeps the selected `WeaponMode` inside that loadout every frame, so the fire, lock-on, and crosshair systems trust it as-is). Login hands each player a portal slot (`PortalAssignments` in `server/src/portals/resources.rs`; `SInit.player.portal_access` seeds the client and `Player.portal_access` in every snapshot keeps it current): in `both` mode every slot owns a pair and left/right click send `CPortalShot` for ends A/B; in `single` mode adjacent slots share a pair, alternate A/B, and place their assigned end with left click. A lone `single` player holds both ends of their pair under the same pair id; a second login splits the ends again and removes the end the newcomer now controls (login runs `PortalMap::remove_access` on every fresh assignment, mirroring disconnect). `PortalMap` in the same file is the authoritative store, keyed by pair; the snapshot list and `PortalSet` are derived from it. The firing client raycasts the aim (`portal_surface_along_ray`) onto world geometry on any carrier — pure point + outward normal, no wall/floor/ceiling taxonomy (`client/src/input/portals.rs`). Closed barriers, powered bridges, and equipment erasers always stop portal shots; the shared ray filter (`portal_surface_along_ray` in `common/src/physics/world/rays.rs`) owns the rules. None is a portal host, and changing plate state does not remove existing portals. The firing client validates placement with `compute_portal_placement`: the whole aperture needs solid backing on one carrier (so an aperture straddling a tile's edge does not fit) and clear front space, and must not cover wall lights or — for standable portals — pressure plates; portal host permissions come from the host map’s texture catalog, checked per face and across the whole aperture (`world/portal_backing.rs`); an incompatible hit broadcasts `SPortalFizzled` for the carrier-attached flash, collapsing ring, sparks, and sound (`client/src/vfx/portal_fizzle.rs`) without changing placed portals. A failing geometric fit bumps Portal-2-style to the nearest fitting spot (`nudged_center`) and dry-fires when nothing fits. The rim-scaled aperture is about 1.48 × 2.76 m, so a tile takes a portal only when its short side clears that: obby's tiles fit with slack, and a tile in a cell under about 3.25 m never does. A portal names its carrier (`Portal.carrier`), and its `pos` and normal are in that carrier's frame, so the wire value stays constant while the carrier moves and every equality-based dedupe keeps working; both sides resolve the world frame from their own `Carriers` (`PortalFrame::from_portal`, `PortalPlacement::portal` does the world → local step), and the client's `carried_portals_refresh_system` re-places carried gates each tick between the carrier advance and character movement (the server stores placements only and keeps no `PortalSet`). Overlap validation compares against the other portals at the current tick only, so a static portal beside a carrier's path or two carried portals out of phase may coincide later; two gates then overlap and nothing breaks. The client checks overlap before sending its carrier-local placement or fizzle impact in `CPortalShot`, tagged with its body generation. The server trusts that geometry while checking generation, assignment, equipment, cooldown, and shared overlaps (`server/src/portals/spawn.rs`); an accepted placement plays `portal_fire` flat for the shooter and spatially at the shooter for everyone else. Gun expiry, death, equipment erasure, and disconnect remove only the end(s) controlled by that player; gun ownership does not change portal slot assignments. `server/src/portals/equipment.rs` removes unequipped players’ ends after timer expiry and after lifecycle/item handling. They ride `SSnapshot.portals`, with `SPortalOpened` as the placement cue.

Traversal is true pass-through in `common/src/physics/portals/traversal.rs`; placement and overlap validation live beside it in `placement.rs`. Each linked aperture knows its backing colliders (whatever its backing volume touches that lies flush behind the plane, so a stacked wall's trim strip opens with the wall while an adjoining ramp or the floor in front stays solid); while a character's body is in the aperture's front corridor, the movement step excludes them (`PortalSet::collision_exclusions`/`movement_collision_exclusions` → `CharacterEnvironment.portals`, the owning client's player only — actors never fall through, and remote players use reported crossing boundaries). A gate's backing is the flush colliders of its own carrier, taken once (a rigid carrier keeps them), and its `carry` is the carrier's travel this tick: the hop tests judge the body's motion relative to the moving plane, and a body inside a carried aperture rides the carrier until it crosses (`PortalSet::transit_carrier`; the rule and its WHY sit at the top of `step_character_movement`), so it exits with carrier-relative velocity. The owning client calls `PortalSet::player_hop` (taking a `PlayerHopBody`) and `CharacterPortalHop` state helpers: the tick the body's center crosses the plane, it continues from the paired end with position mapped continuously (aperture offset + penetration carried; the offset clamp is also what lets a steering player escape a fall chain), velocity split into vertical velocity, `AirborneMomentum`, and any separately mapped blast knockback, and the persisted movement intent mapped so held input immediately points out of the exit. Each client ranks `projectile_hop` against its other bullet collision events. The aperture frame derives from the surface normal alone (world-up projected onto the plane; shooter yaw only where that degenerates), so ramps work unchanged. Two touches keep hand-placed floor/ceiling fall loops alive: the yaw of a vertical-normal placement snaps to quarter turns (`portal_placement_yaw`), and a body flying toward such an aperture is funneled toward its axis unless the player is steering (`PortalSet::funnel_displacement`, applied inside the shared movement step).

Client portal surfaces are off-axis render targets (`client/src/portals/render.rs`). Each active presenting camera roots its own view chains — the main camera through the shared surfaces, the rearview mirror through a replica set on its own layer — so the mirror sees through portals from its eye. Every disc carries a `PortalSurface`, and a carried portal's discs follow its carrier each render frame at the carrier's interpolated pose (`portals/transform_sync.rs`); the view chains resolve their frames at that same pose. Every complete root is built while the roots fit the budget; with more roots than budget, each presenter builds only the largest on screen, so the graph then follows the view. Views are built as deep as the budget could admit (budget − 1 hops, so one pair can fill it) under fixed camera/surface entity caps, deepest rendering first; `ClientSettings.preferences.portal_view_budget` — the settings menu's "Portal views" — is the one user-facing knob: it caps the views each presenting camera renders per frame, largest on screen first, a nested view only under its admitted parent (0 = no see-through). Portal cameras render linear HDR with tonemapping and grading off, so the presenting camera tonemaps once. A view is active only while its aperture has a screen footprint at every hop of its chain — computed from this frame's camera, not read back from last frame's visibility — and a surface shows its view texture only while that view renders, its emissive glow otherwise. Each view renders only the on-screen part of its aperture (the aperture clipped by the view frustum) — the portal frustum is that sub-rectangle and the surface's `uv_transform` maps the disc onto it — so a texture never needs more pixels than its presenter has; its size is picked per axis from a power-of-two ladder off that footprint with shrink hysteresis, and each camera retains only its current and immediately previous immutable target buckets. The local player's meshes use a separate render layer: portal and shadow cameras include it, the first-person camera excludes it, and the debug view includes it. Camera-facing player/actor labels use a main-view-only layer, and each scene camera gets its own layered sun/moon disc so mapped views preserve the celestial direction.

Only the owning client crosses a player (`client/src/portals/transit.rs`), mapping movement and camera immediately through `portals/view.rs`: out of a wall the camera keeps the mapped view and blends its tilt away, out of a floor or ceiling it keeps the horizon and its pitch and turns its yaw the way the held input turns. It sends an immediate movement report. The repeated crossing marker makes observers cut between entrances and exits without acknowledgments; `common/src/protocol.rs` owns the ordering rules. A body halfway through an aperture is drawn on both sides of the plane: while a player's body straddles a gate (`PortalSet::straddled_gate`), `client/src/portals/clipping.rs` shows the hidden twin model every player carries at the paired end with the model's pose mapped through the pair and its animation state copied (not for the local body in first person, which is not drawn), judges the gate where it is drawn, and on the handoff turns the upright body from the twin's mapped pose back upright about its centre over `PORTAL_VIEW_BLEND_SECS`, and gives both models a `PortalClipMaterial` (`client/src/materials/portal_clip.rs`) that discards fragments behind their own gate's plane in the main, prepass, and shadow passes, so neither half shows through a backing.

#### Ladders

Freestanding climbable elements anchored on a grid edge (`{lower_level, col, row, side, levels}` in the map JSON, top-level like ramps) — no wall or floor required, deliberately dumb (nothing inspects surrounding geometry), and one-sided: only the FRONT, the rail side the normal points at, is a ladder. Nothing rides the wire beyond `MapLayout.ladders`, so prediction agrees for free. Climbers ride the ladder's carrier through `CollisionWorld::carried_ladder_at_previous_pose` and `step_character_movement`; collision sweeps and crushing still use the current world geometry.

The shared `step_character_movement` derives everything per tick from position + control intent against the front-only climb volume (`LadderVolume`, a plain AABB — no Rapier collider): pushing toward the rail plane ascends, pushing away descends (intent speed × `movement.ladder_climb_ratio`), idle latches, jump detaches, and an ascending or descending character gets an additive pull along the face toward the center axis that enough sideways movement can overpower. The plane is a fence for front-side characters up to the top landing, open above it (`clamp_move_at_ladder_plane`). From the back a walker passes straight through and emerges on the front face — that is the mid-ladder mount from a balcony behind it — and the volume's overshoots at both ends make the top crest and the bottom grab work.

Actors opt in per kind through `actors.kinds.<kind>.can_use_ladders` (all shipped kinds default to `false`), included in the gameplay bootstrap. `LadderMode::for_actor` combines that permission with the actor's replicated climb/exit intent; ordinary walking ignores ladders. Navigation adds body-checked ladder links to each carrier's floor/ramp graph in `server/src/actors/navigation/ladders.rs`, validating both roam and active speeds with the shared motor. Roam, pursuit, escape, and return routes retain explicit mount, climb, and exit waypoints; climbers finish a traversal before replanning, count vertical progress, and hold their rung when blocked. Mid-ladder targets can be pursued and held at their height. Ladder links stay within the actor's carrier.

#### Carriers

A carrier is a rigid group of map records that slides between two poses, out, held, back, held, its pose a pure function of its run ticks (`common/src/map/carriers.rs`: `CarrierPose`, `carrier_offset_at`, and the `Carriers` runtime both sides advance). A free carrier's run ticks are the shared tick. A switched carrier (`Carrier.switch`, from the nested map's `switch`) runs while its pressure plate kind matches its On/Off response and freezes where it is otherwise; its `CarrierRun` — the run ticks it had at a stamp tick and whether it has run since — rides `PlateState.carrier_runs` in every snapshot, so both sides still place it from the shared clock and that small value, and a client that learns of a flip late corrects once. It starts at its `phase_secs` offset, moving immediately for an Off response. The world is the implicit carrier 0 and never moves; `MapLayout.carriers` lists the others, parents before children, and every layout record names its carrier and is expressed in that carrier's frame (world space on the world carrier). Every carrier is a nested map (below); a moving tile is the one-cell `tile` map nested where it should slide. Nothing per free carrier rides the wire. Both sides run the shared `carriers_advance_system` right before character movement: it steps every carrier to this tick's pose from the tick and the plate state and moves its colliders and ladder volumes (`CollisionWorld::set_carrier_poses`, the one place a collider ever moves), and, on the client, `carried_portals_refresh_system` follows with the carried portals. A carrier's colliders are ordinary world geometry, so sight and every ground query see a tile like a floor. Riding happens inside `step_character_movement`: the support probe names the carrier under the feet (`supporting_carrier` in `characters/support.rs` owns the support rule and its rationale), the vertical part of that carrier's displacement moves the body before the ground probe, and the horizontal part rides the move so walls still block; a body that leaves a carrier keeps its velocity as `AirborneMomentum` (the portal launch velocity, generalized) and its rise or drop in its vertical velocity. Actors are carried like players but keep no momentum when they leave a carrier. Ground actors navigate carrier-local grids and can cross physically connected floors between carriers. Their route frame follows the carrier supporting their feet; spawn ownership and the roaming volume remain with the original zone. Leaving a carrier does not despawn an actor. The client spawns one root entity per carrier at bootstrap (`client/src/carriers/`, `CarrierEntities`), interpolated between its last two tick poses like a character, and every map entity hangs under its carrier's root at its local transform, mesh batches keyed by carrier too, so textures are projected in the carrier's frame; `CarrierStoreys::tag` turns a record's local level into its world `MapLevel { level, span }`, the span covering the carrier's motion, and one rule (`map_level_visibility`) drives level focus for every map entity. Nothing keeps a carrier's path clear: `CollisionWorld::push_character_from_carriers` in `world/carrier_contacts.rs` resolves incoming side contacts through the character controller before control movement, and any crushing overlap that remains is fatal. Carriers are not Rapier kinematic bodies: those would add an integration step without replacing the riding, pushing, and crushing policies, and both sides already agree on carrier motion from the tick alone. The shared step reports `CharacterMovementResult.crushed` from `CollisionWorld::character_crushed` (which checks capsule penetration after pushing and stepping); the owner reports a crushed player and the server kills it outright (`DeathSource::Crushed`, applied by `players_fatal_outcomes_system`) and kills such an actor through `kill_actor` (`ActorCrushed`, read by `actors_removal_system`). The firing client's carrier pose determines portal placement; the server adopts the submitted carrier-local frame.

#### Nested maps

A map embeds named geometry in its `nested_geometry` object: `nested_maps` in the map JSON, top-level like ramps, is `{map, level, from, to, to_level, travel_secs, pause_secs, phase_secs, from_nudge, to_nudge}` — the named geometry is placed with its cell (0, 0) on parent cell `from` at parent storey `level` and slides to `to` on `to_level`, one leg in `travel_secs`, out, held, back, held; `from == to` on one storey is a room placed once. Each nudge displaces that end from its anchor by `[x, y, z]`, x and z in wall widths across columns and rows, y in floor thicknesses up (zero by default) — two floors meeting at a grid line overlap by one wall width, so 1.01 back along the travel leaves them just clear (`carrier_from_motion` in `compile.rs`). The editor draws each footprint where the map rests, its nudge applied in the canvas plane and its y part written into the label. Each parent that needs a moving tile embeds a one-cell `tile` definition. Nesting is recursive, and each nested map compiles as a carrier: its records stay in its own frame (`definition/geometry.rs`, `compile_geometry`; `definition/compile.rs` owns the tree traversal), its child carriers take the next ids right before they compile so parents precede descendants, and `nested_origin_offset` says where its grid sits in the parent's. `MapSource` in `definition/schema.rs` holds the outer `MapDef` plus named `MapDef` geometry; every placement resolves in that parent document's namespace, including placements inside nested geometry. Every setting comes from the map being played. `definition/load.rs` validates the definitions and rejects missing references and cycles; unplaced definitions do not contribute to the compiled world. Kinds resolve against the root's catalogs, with the nested map's name in the error. Only the map being played needs a player spawn zone (`generate_map`); nested zones join the pool and spawn through the carrier's pose. Grid data is per carrier (`MapConfig.grids`, `CarrierGrid`): player spawns, actor spawn zones, placed items, and pressure plates name their carrier and keep carrier-local cells, and the pickup and plate tests convert through `Carriers::pose`; `Item.carrier` and `SpawningActor.carrier` ride the snapshot so the client parents each item and beam-in ghost under its carrier. Random items use the root grid alone; missile airspace uses centers from every carrier grid. Nothing checks for overlap: a nested map's outer slabs overlap the parent's by the floor extension wherever they touch, and a sliding one sweeps whatever lies along its path. The editor's "Nested Maps" group (`tools/map_editor/nested_maps.py`) places, moves, edits, and erases entries and draws each end's footprint from the document's current named geometry.

#### Weather & lighting

Each map selects a named skybox with `settings.json::skybox`. `assets.json::skyboxes` owns its image, rotation, and `celestial_disc` (direction, visibility, size, and bright/dim/dark luminance and phase); hidden discs retain their directional light. `client/assets/convert_skybox.py` converts equirectangular panoramas into the 4×3 PNG cross and reports a light direction from a source pixel; usage is in `client/assets/README.md`.

Both are continuous state in every snapshot, seeded from the map's `weather`/`lighting` mode (a concrete state, or `auto` for the global cycle). `weather_system` runs the rain cycle; intensity rides `SSnapshot.rain_intensity` and the client smooths + renders it (`vfx/rain.rs`).

Lighting is separate — rain does not dim the world — and the wire speaks preset names: `SSnapshot.lighting` is a `LightingBlend {from, to, blend}` between two named client-side looks (`bright`/`dim`/`dark`, world illumination in `client.json` and disc looks in the selected skybox asset; a plain preset is the degenerate `from == to`). `light_cycle_system` runs the cycle — a wrapping clock over `cycles.lighting` (hold at each present stop of `bright_secs`/`dim_secs`/`dark_secs` — any two or three — fading between adjacent stops; `blend_at` is the pure timeline→blend map). The client's `lighting_blend_system` resolves the names and eases every channel toward the blended look in look space — intensity channels in log space, so fades are perceptually even — and cycle steps, segment crossings, and admin jumps all fade with one mechanism.

`/weather` and `/light` report current state; `/weather rain|clear|auto` and `/light bright|dim|dark|auto|<0..1>|<from> <to> <0..1>` hold a state (named looks are absolute, numeric holds are cycle-relative) or resume the cycle continuously.

#### Actor lifecycle

`actors_removal_system` routes health-zero deaths and crushes through `kill_actor` (explosion blast + `SActorDeath`); ground-actor falls are silent; flying actors have no fall removal rule. Crushes award no kill credit. `actors_respawn_system` batch-refills every missing slot in a zone after the zone's `respawn_secs`; `null` disables automatic refills. A zone with a `switch` spawns only while that pressure plate kind matches its On/Off response, and the switch never touches its countdown: a zone switched off at boot is left due (`Reset`) and fills the tick its switch allows, a kill counts down whether the zone is on or off, a due zone its switch holds back keeps its timer entry and fills once the switch allows, and switching off and on again neither restarts nor skips a countdown (`ActorSpawnZone::is_enabled` is the one gate). A zone whose condition already holds at boot fills like an unswitched zone. A `scope: all` reset removes a switched zone's actors, which return only while the zone is enabled, and a beam-in already pending when the zone is disabled still materializes. The map’s `respawn.actors.on_player_death` selects the shared `never`, `solo`, `any`, or `all` death/logout trigger, and `scope` selects `dead` (preserve survivors and pending spawns) or `all` (replace both). `reset_actors` in `actors/spawning.rs` bypasses automatic cooldowns and disabled refills, then the normal spawner fills the vacancies without destruction effects or rewards. Replacements are queued into `PendingActorSpawns` with ids, unoccupied spots, and headings reserved. `actors_pending_spawn_system` materializes each entry after `actors.settings.spawn_warning_secs`. Each pending spawn carries the tick it was reserved and the tick it is due (`SpawningActor`); both sides read the shared tick against them, so the ghost's fade is a pure function of it and nothing counts down or resyncs. During the window the actor doesn't exist server-side and clients render a ghost from `spawning_actors`.

Actor and player spawn zones span `levels` storeys from `level` (default 1). Actor Count applies once to the whole volume. Immovable actors spawn at unobstructed cell centers (`ActorSpawnZone::immovable_cells`), including bridge and unsupported cells; validation imposes no floor-capacity limit. Live and pending positions reserve centers. When none is free, a zone enters `ActorRespawnState::WaitingForSpace`, logs once, and retries each tick; a movable zone with a respawn delay uses that delay for automatic retries. Flying actors sample clear air throughout the spawn volume, without floor support, and recheck geometry and body clearance before materializing. Movable actors retain random placement; death-triggered refills start in `ActorRespawnState::Reset` and wait for space until every slot is filled.

A blocked flying reservation is canceled and its zone waits for a fresh position and warning window. The client emits materialization effects only when the matching actor appears; canceling a reservation produces no materialization burst.

#### Actor AI

Contact, beam, and contact+beam attackers have separate decision controllers selected by the tagged `attack` config. Decisions normally run at 10 Hz, with pending navigation continuing each tick (an immovable actor decides every tick, since firing is its only decision); route following, collision, beam damage, and timers run at the configured server tick. Each actor spawn zone owns `roam_distance` in metres, default 0: the shortest Euclidean 3D distance from the actor's movement center to the authored spawn volume. Zero keeps roaming inside that volume. `server::map::ZoneVolume` supplies the shared boundary calculation, independent of collision clearance and navigation routes. Pursuit and evasion may leave the roaming volume; return routes find a reachable part of it.

`navigation/ground/` owns floor graphs, ramps, ladders, and searches weighted by travel distance. Searches check current barriers and powered bridges and join carrier grids only across physically walkable connections. Routes retain a carrier-local prefix through the next crossing, then replan in the supporting carrier's frame. Ground pursuit chooses reachable attack positions, including for airborne targets. Both navigation systems spread searches over ticks under per-system work budgets; ground queries retain failures until their inputs change. Roaming explores reachable nodes with bounded work, while flying homes keep bounded samples through geometry-aware refreshes. `navigation/air/` preserves usable routes during replacement searches and checks the full movement capsule in 3D. Flying kinds select `locomotion: flying`; they use world positions, no gravity or ground attachment, and the per-map roam/active speeds in every direction. `behavior/beam.rs` shares beam decisions and `behavior/geometry.rs` shares attack-position, 3D threat-distance, and cover checks. Flying movement samples use the world carrier.

Anti-jam handling: two route-construction rules (`NavGraph::anchor_route_start`; `waypoint_passed` in `behavior/tick.rs`) plus stall recovery via the shared `ProgressWatchdog` — a stalled actor hops to a random neighboring cell before rethinking (`shake_loose`). The WHYs live as comments at those definitions.

Ramp waypoints use the compiled slope height in `Cell::ramp_center_y`, including the opening above the ramp's top cell. `CollisionWorld::character_ground_route_clear` checks slope transitions without leaving the route's horizontal line. Floor slabs stop at ramp landings (`map/floors.rs`); the editor's `floor_footprints.py` keeps the same bounds.

Threats are acquired by LOS within spherical vision and retained for `actors.settings.threat_memory_secs` after contact is lost, then actors return home. Reachable attacks outrank evasion; contact actors evade unreachable players, beam actors evade during beam cooldown, and contact+beam actors move by contact rules while firing their beams opportunistically (the beam target lives in `BeamState::Firing`). On a map with no placed/random single-shot, multishot, or missile pickups (`MapItems`) nothing evades: an unreachable player is ignored. Evasion picks stable cover in a bounded local search and revalidates it as threats move; with no cover in reach the actor flees instead, toward a reachable position farther from threats, keeping each leg until it ends (`ActorMode::Evade { fleeing }`). Both navigation systems prefer wide threat clearance, relaxing it only when necessary, and vary suitable flee destinations; roaming recovery stays within the zone extension.

`/peace [on|off]` toggles `ActorMap.peaceful`: actors forget targets and roam without attacking, including contact detonation. `SSnapshot.actors_peaceful` clears beam effects on clients. The server startup flags `--god` and `--peace` initialize `Invincibility` and `ActorMap.peaceful` to enabled in single-player, host, and dedicated-server modes; the console commands still toggle that state during play.

### Conventions

- Do not include the user's real name in repository content.
- This is pre-release software: JSON configs, map files, and the wire protocol are intentionally unversioned, and breaking changes are allowed. Update every producer, consumer, fixture, and checked-in config together; do not add version fields, compatibility branches, or migrations unless this policy changes. The one exception is the gitignored `config/client/client_local.json`, which git cannot update — see its entry above.
- Entity IDs are newtype wrappers: `PlayerId(u32)`, `ActorId(u32)`, `ItemId(u32)`, `MissileId(u32)`, `BarrierKindId(u16)`.
- Bevy resources `PlayerMap` / `ActorMap` / `ItemMap` / `MissileMap` map IDs to entities on both sides.
- Shared player/actor behavior belongs in `characters` and is named accordingly. Portal systems own portal behavior; general movement and gameplay effects must run without portal traversal.
- Living local players are repositioned only when a spawn or explicit relocation establishes a new body generation; a dead local body stops stepping where it died. Remote players, actors, and observed missiles play buffered samples through the one `SampleBuffer`, without physics or reconciliation. Missiles simulate only on their shooter.
- Crossbeam channels carry decoded `ClientMessage`/`ServerMessage` values: every sender holds a shared handle, and one system per frame hands the batch to renet, so gameplay code never touches the transport and the server's broadcasts do not know which players are remote. Receiving from a remote link is direct. The host's own client holds the other ends of its embedded server's queues, so nothing is serialized or forwarded in-process. A closed queue is the disconnect in both directions. There is no async runtime.
- Coordinates: Bevy Y-up `(x, y, z)`, units in meters.
- Wire format: `bincode` 2 (binary).
- `score` (server `PlayerInfo.session.score`, client `PlayerInfo.score`, wire `Player.score`) accumulates per-event deltas from the server config's `scoring` block and persists across deaths. Don't confuse with `health`.
- "Dead": on the server, `PlayerInfo::is_dead()` means its per-life lifecycle is `Dead` (an individual timer) or `GroupRespawn` (the timer lives on `PlayerMap`), neither of which owns an entity. On the client, `LocalPlayerInfo.is_dead` is a separate flag. Don't try to unify the two — they live in different crates.
- Keep gameplay concepts (`Wall`, `Floor`, `Ramp`, `Barrier`, items, spawn zones) in map/protocol types; keep movement/collision behaviour both crates run in `common::physics`; code only one crate runs lives in that crate.
- Mesh UVs are computed from the record's position in its carrier's frame (world position on the world carrier), not from the mesh's local position. Floor/wall/ramp builders in `client/src/map/spawn/` take `carrier_center` (and `rotation` for walls); each vertex's UV is `(carrier_center + rotation * local_pos) · uv_axis / tile_size`. New mesh builders should follow the same pattern; a carried mesh's frame moves with it, so its texture never swims.

The editor reads `config/client/assets.json` (wall-light kinds, watched) and `client/assets/symbols/items.json` (item glyphs); texture images are neither read nor watched.
Jump Reach (`jump_reach.py` and `jump_reach_overlay.py`) shows persistent per-power-up landing markers: dots for no damage, triangles for damage, crosses for fatal landings at full health. It reads the parent map’s `player_fall` thresholds and global maximum health; synchronization comments in `server/src/players/falling.rs` identify the shared damage rules.
Run Time (`run_time.py` and `run_time_overlay.py`) labels every cell on the origin's level with the straight-line seconds between cell centres at the map's run speed and with the speed power-up; it ignores walls and ramps and reads only `geometry.grid_cell_size` and the `movement.player` speeds. Both tools take their numbers through `setting_number` in `catalogs.py`.
Player and actor spawn zones have no ground-support or floor-capacity checks in the editor; surface suitability belongs to the map designer. Zones remain one object across their level span. Numeric spawn-zone ordering and deduplication match the server while preserving invalid authored values for validation. Actor zone Controls sets the span and roam extension in metres; View → Show Roam Extensions (`R`, disabled initially) toggles the rounded boundary, including its cross-section above and below the zone.
Checkpoint zones reuse the spawn-zone move/resize interactions and have their own placement and erase tools. The toolbar's Type selector chooses Individual, Group — any, or Group — all; right-click edits an existing zone's type. They require flat accessible floors; region operations treat each rectangle as a whole object and preserve its type.
`MapDocument` owns edit transactions and undo history; `editing.py`,
`erasing.py` (with the `ERASE_GROUPS` table behind every `Erase <group>` tool),
`regions.py`, `transforms.py` (including level insertion and removal), and
`nesting.py` (nested-map motion, shape, and cycle checks) hold widget-free map
operations that import no Qt, and every operation works in grid units
(`viewport.py` converts once, at the canvas; edge picks share one tolerance from
`EDGE_PICK_PIXELS`).
Loading keeps invalid records; `repairs.py` proposes explicit undoable repairs
across the outer map and every nested definition, and the issues dock navigates
to them. Tool properties sit in the toolbar and
placement reuses them; feedback is a temporary canvas notice.

## Adding a texture

Texture sets are freepbr.com UE packs. Follow this workflow for every added pack, including model-generation sources. Catalog entries are metadata; load texture images only when a material is used.

Use a distinct model texture only when it contributes visibly at normal gameplay distance; reuse an existing material for tiny details. Generated models share catalog PBR loading and metre-scaled UVs in `client/assets/models/modelkit/materials.py`. Each model has a matching `.json` beside its GLB for material tuning; rebuild the GLB after changing it (controls and commands in `client/assets/models/MATERIALS.md`).

1. Prepare the pack outside `client/assets`; keep only used texture maps in `client/assets/textures/<name>-ue/`. Textures embedded in active models and inputs needed to regenerate them count as used; unused variants, height maps, and previews do not.
2. Build the packed metallic-roughness map Bevy wants (needs ImageMagick): `client/assets/textures/combine_metallic_roughness.sh <dir>/<name>_roughness.png <dir>/<name>_metallic.png` writes `<name>_metallic-roughness.png` next to them. `multiply_intensity.sh <metallic-roughness.png> [roughness_add] [metallic_multiply]` retunes it afterwards (keeps a `.original.png`).
3. Copy the required maps, including the packed metallic-roughness map, into the asset directory. Add a `materials.<name>` entry in `config/client/assets.json`: `textures.base_color` (`_albedo`), `normal` (`_normal-dx`; the name must carry `-normal-dx` or `-normal-gl`, since the client flips DirectX maps and both loaders reject an unsuffixed name), `occlusion` (`_ao`), `metallic_roughness`; `tile_size` in meters; `repeat` and `linear_data_textures` true. Use a neutral white occlusion image when a pack has no AO map.
4. Bind an alias to the material in `assets.json::aliases`. Enable it in a host map’s `settings.json::textures` with an explicit `portalable` boolean when that map needs it. Map faces use those aliases; the ladder's `material` binding names the texture set directly. Pressure plates use the materials embedded in their GLB.
5. `cargo test --release -p client referenced_assets_exist_case_exactly` catches path and case typos.

## Coding style

- Rust edition 2024. Format with `cargo fmt` (see `rustfmt.toml`).
- Workspace lints (root `Cargo.toml`): `unsafe_code = "forbid"`; `unwrap_used = "warn"` — prefer `expect("…")` with a message, or proper error handling; `todo = "warn"`.
- Naming: `snake_case` functions/modules, `CamelCase` types, `SCREAMING_SNAKE_CASE` constants.
- Reserve `constants.rs` for appearance, gameplay, and performance tuning; keep implementation details beside their owning code, with shared definitions where consumers must agree.
- In `constants.rs` files, constants that logically belong together share a descriptive prefix and stay grouped together (for example, `MISSILE_EXHAUST_*` and `EXPLOSION_*`). Constants defined in other files are exempt from this grouping and prefix rule.
- Imports are nested `use` trees wherever possible (one `use` per crate root, paths grouped in braces); no `use ... as` renames unless a name collision leaves no alternative.
- Do not introduce `Arc` just to make borrowing or ownership convenient. Reserve it for genuine cross-thread shared ownership or APIs that require it; otherwise prefer references, owned values, IDs/indices, or restructuring ownership.
- Use `assert!` / `assert_eq!` / `assert_ne!` for invariants — never `debug_assert!`. Only release builds run, so `debug_assert!` is a no-op.
- `mod.rs` files contain only `mod` declarations and `pub use` re-exports (attributes like `#[cfg(test)]` on them are fine) — no functions, types, or impls. Code that would land in a `mod.rs` goes in a named sibling file (e.g. `plugin.rs`) and gets re-exported.
- A module with submodules uses `<module_name>/mod.rs`; never pair `<module_name>.rs` with a sibling `<module_name>/` directory.
- Default to writing no comments. Only add one when the WHY is non-obvious: a hidden constraint, a subtle invariant, a workaround. Don't explain WHAT well-named code already says.
- When a code comment is the authoritative description of a rule or invariant, point to it from `AGENTS.md` instead of duplicating it; keep one source of truth.

## Testing

Add tests selectively for algorithms, state transitions, interactions, persistence, and meaningful regressions. A code change does not automatically need a new test. Do not test cosmetic tuning, trivial getters, duplicated constants, or restatements of the implementation. Remove redundant coverage while preserving distinct failure scenarios. When a test breaks, decide whether it caught a bug, needs simpler setup, or should be removed before updating expectations.

A shared fixture may load a shipped configuration file as the base of a whole-schema value (`ClientSettings`, the server's `GameplayFile`); every test pins the values its assertions depend on, so a tuning change never moves a test's expectations. Whatever can be small stays test-owned: the test map, the asset catalog, and the JSON that loader and serialization tests write to temporary files. Shared fixtures return fresh values. Do not copy a shipped file into a fixture, or add production defaults just for tests. Editor fixtures install their catalogs before constructing windows or documents, including file watchers and command-line entry points.

`cargo test --release --workspace` is the canonical command. Unit tests live
in a `tests/` directory beside the module they cover, one file per source
file: the tests for `physics/abs.rs` are `physics/tests/abs.rs`, declared at
the end of `abs.rs` with `#[cfg(test)] #[path = "tests/abs.rs"] mod tests;`,
so `super` is the module under test and private items stay reachable. Tests
that cover a whole directory module are declared from its `mod.rs` the same
way (`tests/<name>.rs`, module `<name>_tests`) or as that directory's
`tests.rs`/`tests/mod.rs`; `include_str!` paths in a test count from the
`tests/` directory. Shared fixtures live under `tests/` beside the code they serve and keep
their module names through `#[path]`: `common/src/tests/geometry.rs` and
`server/src/tests/geometry.rs` (`test_geometry`), `client/src/tests/fixtures.rs`
with its JSON in `client/src/tests/fixtures/` (`test_fixtures`), and
`server/src/config/tests/fixtures.rs` (`config::fixtures`). No source
file holds an inline `mod tests`, and there are no crate-level `tests/`
integration-test directories. Name tests after what they assert
(e.g. `lethal_hit_returns_true`, `matching_keys_open_all_barriers_of_their_kind`).
The map editor's headless `unittest` suite lives in `tools/tests/` and covers
its pure geometry, normalization, resizing, and validation helpers.

Shipped models may be loaded for compatibility checks using an explicit
test-owned model catalog. Assert only runtime requirements (rig node names,
clip indices, the emissive/housing split, texture colour spaces), never
incidental material or texture counts or unrelated bone names. Do not read
`config/client/assets.json` to configure these tests.
`client/src/tests/assets.rs` (module `test_assets`) is the headless app
every such test loads through: spawn models with `load_character_model`, preload bare GLBs with
`preload_gltfs`, then `settle` before sampling; it fails a test whose scene
was spawned twice.

## Security & assets

- **Current threat model:** development and private/LAN play assume cooperative clients. Abuse hardening — client rate limits, per-tick ingress budgets, bounded/backpressured network queues, flood protection, and admin authorization — is intentionally deferred. Revisit it before any public release or publicly accessible server.
- `client/assets/` are not open source — replace before publishing a fork.
- netcode runs in unsecure mode: sessions are encrypted with the zero key, so anyone who can reach the port can join. Fine for LAN play; revisit with the hardening above.
