# Repository Guidelines

## User privacy

Do not use the user's personal name in responses or add it to documentation, examples, test fixtures, comments, generated assets, or attribution. Use neutral wording and fictional sample names. Avoid recording identifying usernames or absolute home-directory paths in project files.

## Follow-ups

Read [TODO.md](TODO.md) at the start of a task and keep it updated when discussing or completing follow-ups. Organize outstanding work into Fixes, Enhancements, and Testing, without deferred/proposed categories or repeated approval labels; listing an item does not authorize implementation. A Fix is behaviour that is wrong; style and cleanup work is an Enhancement. Remove completed items.

## Project structure

Rust workspace. The root package builds the one `cuboid-wars` executable: `src/main.rs` parses the CLI and picks the mode from one optional flag (`--host`, `--join`, or `--serve`, each with an optional address; none is single-player), and `src/host.rs` runs the embedded server thread for the two modes that play and serve at once.

Entries below name a module's role and point at the comment that owns each non-obvious rule. Mechanisms, tuning numbers, and step-by-step behaviour live in the code; read the module before changing it.

- **`common/`** — shared between client and server.
  - `math.rs` — shared math helpers, `sequence_is_newer`, `PHYSICS_EPSILON`, and the glam ↔ Rapier conversions every physics file uses.
  - `celestial.rs` — the solar/lunar model and the tick-anchored celestial clock shared by the server and renderer.
  - `protocol.rs` — all `ClientMessage` / `ServerMessage` variants and wire structs. Read the top-of-file doc comment before adding a message: it defines the bootstrap / state / cues / events roles and the two lanes.
  - `network.rs` — the wire definition on renet (channels, bincode codec, netcode protocol id). The header comment is the authority; a message's lane comes from its role in `protocol.rs` (`Lane`, `lane()`).
  - `physics/` — what both crates run: the shared character motor (`characters/`: `step_character_movement`, support and ladder rules, velocity components, move-plan intersection), the collision world (`world/`, one `impl CollisionWorld` per concern: construction, rays, ball casts, ground probes, character queries, flight, bounds, portal backing, field filtering in `colliders.rs`, ladder volumes, carrier sync and contacts), field passability (`fields.rs`), the blast falloff rule (`blast.rs`), the stall watchdog (`watchdog.rs`), and portal geometry and traversal (`portals/`). Generic collision queries stay with `CollisionWorld`; navigation policy belongs to its caller. Carriers are the one geometry that moves: `world/carrier_sync.rs` places their colliders each tick.
  - `types/` — shared markers, IDs, player body generations, positions, movement states, map layout types, items and power-ups, snapshot records, feed spans, texture settings and their validators, the shared clock (`tick.rs`), and the kind tables (`kind_table.rs`, the one `KindTable` behind `FieldTable` and `SwitchTable`; `field.rs`, `switches.rs`, `switch_state.rs`).
  - `map/` — shared map behaviour: ramp geometry (`ramps.rs`), carrier poses and runs (`carriers.rs`), grid ↔ carrier conversion (`geometry.rs`, `MapGeometry`), and the exterior grounds, their footprint, and rocks. Per-map sizes ride `MapSettings.geometry` (`config/geometry.rs`); fixed world sizes are in `constants.rs`. Layout records are in their carrier's frame (world space on the world carrier) and the server fills `y`/`height` at compile time, so physics and the client place them without the map's sizes and only grid logic needs `MapGeometry`.
  - `health.rs`, `constants.rs`, `config/` — the `Health` type, gameplay constants, and the shared configuration types; `config/network.rs` holds `NetworkConfig` and `UpdateCadence`, the send-rate ticker both crates run.
- **`map_core/`** — map source rules shared by the game and editor: `schema.rs` (source types, imported directly by the server), `load.rs` (typed loading and preparation), `diagnostics/` (the shared validator; the comment at `Issue` says what is an error and what a warning), `authoring/` (normalization, canonical ordering, explicit repairs, placement checks), `transforms/` (resizing, level edits, rotations, mirrors), and `geometry.rs` (ramp footprints, landing edges, and slab extensions for both the server compiler and the editor). Validation never repairs a document; game loading rejects invalid sources, while the editor keeps invalid values for diagnosis and undoable repair. Documents keep their authored key order (`serde_json`'s `preserve_order`), so a save rewrites only what was edited.
- **`map_core_py/`** — thin PyO3 adapter over `map_core`, built as `_map_core` by Cargo on first use in each editor process. There is no Python fallback for map rules; the comment at `grid_int` in `tools/map_editor/core.py` names the coordinate helpers that stay in Python, which `tools/tests/test_core_parity.py` holds to the Rust results.
- **`server/`** — authoritative headless server (Bevy `MinimalPlugins`).

It installs function-style domain plugins, matching the client; each domain's `plugin.rs` owns its system registration and its `resources.rs` its Bevy resources. `schedule.rs` defines the cross-domain tick order (`Prepare` → ingress → behaviour/movement → combat damage/removal/explosions → lifecycle/maintenance → snapshot) and where deferred commands flush, so ID maps never expose unmaterialized entities to network collection.

Above it: ingress (`incoming.rs`), authenticated routing (`routing.rs`/`handlers.rs`), login, snapshots and movement broadcasts (`snapshot.rs`/`broadcast.rs`), server-rendered feed lines (`feed.rs`), and admin commands (`admin/handler.rs` owns authorization and replies, `admin/command.rs` the grammar and `/help`, `admin/execute.rs` world mutation).
  - `actors/navigation/surface/` — the only ground navigation, used by every movable ground kind in every map; there is no cell graph or second backend, and grids remain for authoring, spawning, and item placement only. `mesh.rs` and `contours.rs` bake the Rapier geometry exported by `common/src/physics/world/meshes.rs`; `world.rs` caches per-body, per-carrier meshes and rebuilds them in the background when fields or quest-locked plates change, serving the previous mesh meanwhile (comments on `BakedSurface`); `regions.rs` adds bounded on-demand windows beyond the authored grids, whose bounds are preloaded coverage, not a gameplay leash; `baking.rs` runs one background bake at a time; `route.rs` and `corridor.rs` find and smooth routes under a shared per-tick visit budget; `ladders.rs` and `transfers.rs` connect ladders and carrier docks; `actions.rs` defines the explicit traversal actions. `actors/movement/traversal.rs` executes them through the actor motor, and `movement/surface.rs` owns replanning, ladder occupancy, soft separation, swept actor blocking, standoffs, and complete motor results. Each non-obvious rule is a comment at its code (voxel resolution, `closest_on_polygon`, the contour and smoothing fallbacks, rear-mount clearance, the probe, sidestep, progress, and territory-boundary rules in `traversal.rs`, the passive-motion reservation, standoff, and player-body rules in `movement/surface.rs`). A walk stalled on a body fails as `RouteFailure::BodyBlocked`; accepted ground moves reach `characters_movement_system` through `SurfaceActorMoves`.
  - Runs at `network.server_hz` (default 30) via the manual `app.update()` loop in `run_server_loop`; server `Time` advances one configured tick per update (`TimeUpdateStrategy::ManualDuration`), so timers and carriers agree, and an overrun skips wall time instead of stretching a tick. Clients use the same fixed step from `SInit`. `server_hz`, `update_hz`, and `snapshot_hz` share the gameplay JSON `network` block and have matching CLI overrides (`NetworkOverrides`); `NetworkConfig::validate` owns their constraints, run by the server after CLI overrides and by the client on the bootstrap.

## Build, run, lint, format

Do not rebuild executable binaries for the user. They always launch the client and server with `cargo run`; validate changes with `cargo check`, tests, and Clippy instead of preparing binaries for playtests.

Invoke commands covered by saved approval prefixes directly, without shell redirection, environment assignments, or wrappers. In particular, use `/opt/homebrew/bin/blender --background --python <script>` directly so the Blender allow rule matches; capture its output through the tool.

**All cargo invocations in this repo default to `--release`.** Debug builds pull in too much and we don't run them — never silently switch to debug.

After all edits are done, run `./tools/format.sh` before handing the work back. It formats all Rust with `cargo fmt`, hand-written JSON with `prettier --write --print-width 80 --object-wrap collapse`, and Python with `ruff format --line-length 120`. Editor-managed map layouts and local settings are excluded. The formatters must be installed on `PATH`.

```bash
cargo build --release
cargo check --release
cargo run --release                                         # single-player: window + embedded server, no port
cargo run --release -- --host                               # also accepts joiners on 127.0.0.1:8080
cargo run --release -- --host 0.0.0.0:8080 --map hotel
cargo run --release -- --join 192.168.1.100:8080 --name "Player"
cargo run --release -- --join --lag-ms 80 --drop 0.02       # 127.0.0.1:8080 with simulated impairment
cargo run --release -- --serve                              # headless server on 127.0.0.1:8080, loads default_map
cargo run --release -- --serve 0.0.0.0:8080 --update-hz 15 --snapshot-hz 4
cargo clippy --release --workspace --all-targets
./tools/format.sh
cargo test --release --workspace
PYTHONPATH=tools QT_QPA_PLATFORM=offscreen python3 -m unittest discover -s tools/tests -p 'test_*.py'
python3 tools/editor.py hotel                               # edits config/server/maps/hotel/layout.json
```

## Architecture notes

The movement authority split is a settled design choice. The project previously used server-authoritative player movement with client simulation and reconciliation, then deliberately replaced it for better responsiveness. Preserve the existing split in architecture redesigns: shared simulation code and headless testing must retain local movement ownership, without reintroducing server mediation, movement reconciliation, or live input replay. The [protocol header](common/src/protocol.rs) defines the ownership and consistency guarantees.

**Server is authoritative for**: player spawns and forced relocations, actor positions, gameplay outcomes, items, actor behaviour, reported bullet and missile damage, scoring, death/respawn timing, map generation (sent once on connect via `SInit`).

**Client owns**: input and final local movement, its own player's portal crossings, rendering, camera, UI, the death overlay. The server adopts every fresh, finite movement report for the current body, including velocities, momentum, knockback, and support. It retains each report in its carrier frame, resolves riders against the current carrier pose, and runs no player physics; ordinary server updates never reposition the living owner. The owner reports landings, crushing, void falls, and erasure commands reliably, and applies reliable additive blast impulses to its current motion. Respawns and forced relocations advance the body generation and arrive reliably through `SPlayerRelocated`, with snapshots as a fallback.

### ECS system ownership and cadence

Client movement/view input runs in `PreUpdate`, after Bevy input processing and console/settings-menu decisions, through `movement_input_plugin` in `client/src/input/plugin.rs`; its comment owns the dependency order before fixed simulation. `input/movement.rs` documents how jumps survive frames without fixed steps. Weapon selection and display toggles remain in `Update`, and firing still follows camera aim.

Prefer handling discrete state at its change boundary when that keeps the code simple: ingress/lifecycle handlers own network-driven entity state, mode transitions own their presentation state, queries filtered with `Added<T>` handle entities created after initial setup, `Changed<T>` propagates component changes, and asset events drive post-load asset work. Small bounded scans are fine—especially for the game's small player, actor, and item collections—and are better than duplicated indexes, caches, or synchronization invariants. Guard equal writes only when they would wake a concrete change-detection consumer or renderer/UI propagation; a nearby comment should name that consequence.

Each output component has one semantic owner. If visibility or another final value combines multiple inputs, one system computes the complete value; independent systems must not overwrite one another in a scheduled race. Zero-data ECS tags use the `...Marker` suffix. Before adding maintenance bookkeeping, compare its complexity and consistency cost with the bounded work it avoids; optimize only when the simpler scan is meaningfully expensive.

### Message dispatch

Both server and client dispatch decoded wire payloads straight from ingress to one domain handler (`server/src/network/routing.rs`, `client/src/network/routing.rs`). Do not re-emit them as Bevy events: ingress is already a Bevy system with world access and each message has exactly one consumer, so an event layer adds no fan-out, scheduling, or parallelism — it has been tried, and it only obscured the receive-to-handler control flow. Reintroduce events only for a message that gains genuinely independent consumers. Bootstrap happens before the gameplay app runs: the executable sends `CLogin` and waits for `SInit` (`client::network::login`), then builds and validates the app from it; the server spawns the body at login unless placement is blocked or a group respawn is pending. The bootstrap rule that makes this safe without a readiness handshake is in the `protocol.rs` header. Once active, the server drops body-bound messages from a dead player, while `CPing`/`CAdmin`/`CChat` and reports for their in-flight missiles keep working through respawn.

### Protocol model

The message roles (bootstrap, state, cues, events) and the two lanes are defined in the top-of-file comment in `common/src/protocol.rs`; keep the detailed rules there only. Read it before adding a message. Most “X changed” state belongs in `SSnapshot`; a cue only for sub-tick latency, an edge-triggered side effect, or information a snapshot cannot carry; an event only when the snapshot cannot stand in for it.

### Gameplay systems

Each entry gives the rules a map or config author sees, the settled decisions, and where the authoritative code is. Actor kinds and their assets are configuration data: runtime systems select reusable capabilities from configuration and never hard-code actor names, asset paths, or model node names. Player-specific model handling is allowed only when necessary.

#### Death & respawn

`kill_player` in `server/src/combat/damage.rs` is the single death entry point; its function comment is authoritative for the sequence, the scoring, and the callers. `explosions_system` drains player and actor blasts to a fixed point; only missile blasts credit a killer. `PlayerMap` owns the map's `respawn` policy and its countdowns. Deaths and logged-in departures share the `never`/`solo`/`any`/`all` trigger in `common/src/config/death.rs` for actor and switch resets; `respawn.players` selects `individual` or `group` (`players/group_respawn.rs`), and `SPlayerDeath.effect` distinguishes explosions, void falls, and the silent group-respawn presentation. The comment on `players_respawn_system` owns actor-reset timing and the in-flight-shot rule.

Checkpoints are rectangular `checkpoints` zones with a `type` (`individual` saves the entrant's destination, `group_any` everyone's when one player enters, `group_all` everyone's once every logged-in player, dead ones included, has visited) and a `number` that orders the course; checkpoints sharing a number are one respawn point with several rectangles, on any carriers. Number 0 is the start, where every player begins and blocked logins and rescues fall back: the placed map tree must contain one (`validate_document` in `map_core/src/diagnostics/validation.rs`), it has no flag or paint, and its `type` is meaningless. Progress only moves forward, and visits survive death. `players/checkpoints.rs` detects grounded entry after combat; login, respawn, the void rescue, and `/return` share `players/spawning.rs`, which samples a clear spot through `generate_checkpoint_spawn_position` in `characters/spawning.rs`. `PlayerSession.checkpoint` survives death and returns to the start on disconnect; `PlayerMap.shared_checkpoint` supplies later joiners. `Player.checkpoint` and `SSnapshot.shared_checkpoint` carry the claims and the private reliable `SCheckpointReached` cue the moment, under one wrap-aware ordering guard. The client draws flags in `fields/checkpoints.rs` and floor paint in `checkpoint_paint.rs` (`vfx.checkpoints`). `--checkpoint <number>`, `/checkpoint [number]`, and `/return` are the debugging entry points.

#### Barriers & keys

A field is a named force field with one state, as a switch is a named control with one state (`FieldDef`, an entry of the root layout's ordered `fields`: its colour, its optional `switch`, and `initially_on`). Barriers (wall edges) and light bridges (floor cells) are its pieces, each naming its `field`; every piece is solid while the field is on, and the field's key lets its holder through all of them. A key changes what its holder passes, never how a field looks. Barriers share one Rapier collision group and bridges another, each collider is tagged with its `FieldId`, and query predicates filter by field: which queries see which group is stated at `world_collision_groups` and `field_blocks` in `common/src/physics/world/colliders.rs`. The owner's character filter passes its held keys' fields plus the fields that are off (`passable_fields`, `SwitchState.open_fields`); actors get the open fields only. Fields that are on block attack paths while remaining transparent to awareness (`world/rays.rs`), absorb ordinary projectiles, and stop missiles and their blasts. The server merges stacked barriers into one record (`server/src/map/barriers.rs`); the client draws all field surfaces through `client/src/fields/`. HUD key slots follow only the fields a key is placed for (`MapConfig::available_items`).

Each map's `power_ups` defines every power-up kind with `mode: always` (available from login through death and erasure, no pickups of that kind) or `mode: pickup` (requires `duration_secs`; `null` lasts until death or erasure). Configuration lives in `server/src/config/items.rs`; effective ability checks share `PlayerInfo::has`. `placed_items.respawn_secs` is a sparse per-type table: positive seconds respawn, zero allows immediate recollection, omitted or `null` never respawns, and `placed_items: null` makes every placed pickup one-time.

#### Equipment erasers

Walk-through fields authored as per-level `erasers` grid edges. Their volumes in `common/src/physics/world/erasers.rs` detect swept player contact and block portal shots; actors, projectiles, and missiles pass through. The owning client reports `EraseEquipment` while in contact, and `server/src/players/equipment.rs` applies it after item collection, so erasure wins over a same-tick pickup; the server keeps no eraser occupancy state. Erasure clears collected power-ups and missile ammo and preserves always-active abilities, keys, health, score, and quests. Erasers, pickups, and ladders are hand-tested volumes rather than Rapier sensors: sensors would need the collision pipeline for enter/leave events and still the swept test for fast crossings and moving fields, so they would not shrink the code.

#### Light bridges

Barriers laid flat: translucent walkways that are solid and lit while their field is on and a faint ghost while it is off. Authored per cell and merged largest-rectangle-first at compile time (`server/src/map/bridges.rs`, which says why; `bridge_bounds.rs` fits the slabs). Bridges set no floor flags, so item and spawn cells never see them. The client draws them in `client/src/bridges/` with the look, rails, and fade shared through `client/src/fields/`; only the panes fade, and the collision slab keeps its full footprint. Ground actor surface meshes include powered slabs and rebuild in the background when fields change; missile routing checks powered bridge colliders.

#### Switches and pressure plates

The root `layout.json::switches` catalog defines named on/off controls; pressure plates are the current physical input, and any number can operate one switch. Each field, actor spawn zone, and nested map carries `initially_on` (default `true`) and optionally names one `switch`, which flips that state while active: on is solid for a field, spawning for an actor zone, running for a Cycle carrier, and heading for end 2 for a Follow switch carrier. The map-wide `fireworks` show names its switch alone. A target without a switch, or on a switch no plate operates, keeps its initial state; the second is a warning, never an error, so plates and targets may be authored in any order. Each switch configures `activation` (`momentary`, `toggle`, or `auto`: toggle with exactly one logged-in player, momentary otherwise), `reset_on_player_death` (`never`, `solo`, `any`, `all`), and `held` (`any`: one occupied plate holds it; `everyone`: every living player stands on one of its plates, or every plate is held when players outnumber them). `server/src/map/switches.rs` owns activation, resets, target state, and the `SwitchState` projection (`Switches::state` is the one place that reads target state; every change goes through `Switch::set_active`); `pressure_plates/` owns physical occupancy and converts it into `SwitchInput` values. `SInit.switch_state` seeds the client and every snapshot repeats it. The plate chain runs after `server_tick_advance_system` so a flip stamps the tick the carriers advance to. The plates of the fireworks switch are inert and hidden (`SSnapshot.locked_switches`) while a fireworks quest is locked.

Plate collision is deliberately approximate: one fixed box per plate (`PRESSURE_PLATE_HEIGHT`) that both motors use and that follows the plate's carrier, ignoring the model's clipped corners and tread animation. The client samples the plate model's `Activate` animation from `SwitchState.active_switches`; tread colours follow the first field the switch drives unless the switch sets `color` (`assets.json::pressure_plate`).

#### Quests

The selected map's `quests` list loads into the immutable `QuestCatalog`; `QuestBoard` holds only mutable session state. Every `SQuestUpdates` entry repeats the quest's complete client-visible definition and current state, so the client needs no catalog or earlier message, and monotonic merging prevents regressions; group state also self-heals through `SSnapshot.quests`. Each quest has a `kind`, a `scope` (`individual`: own progress and completion; `shared`: one pooled counter that completes once for the group; `everyone`: own progress, completing for the group once every active player reaches the threshold), points, and optionally `requires`, which hides it until the named group quest completes. Kinds advanced by a world event rather than a player (`fireworks`) must be `shared`. `quests::record_event` is the entry point for progress; `/quest` lists the catalog and completes quests by fiat.

#### Character movement

The shared `step_character_movement` takes a `CharacterStep` that separates `control_velocity` from `external_displacement`: ladder interaction reads only control velocity, so knockback can move a body without starting a climb. `step_player_movement` (`client/src/players/movement/step.rs`) and `step_actor_movement` (`server/src/actors/movement/step.rs`) apply owner and actor policy over it. The client's fixed-step schedule (`local_simulation_plugin`) is the owner's simulation, not a prediction: nothing corrects it, a dead local body stops stepping, and only a new body generation moves it. The owner reports its full state at `network.update_hz` in the frame of the carrier it rode; the server keeps the newest report whole in `PlayerLife.movement`, resolves its world position before actor movement, and relays it as received. Server player entities carry only position, facing, and health, and neither the server nor observers run remote player physics. The owner also reports landing impact speed, crushing, void falls, and eraser contact as `CMoveOutcome` events (`players/outcomes.rs` on both sides); the server applies the damage and equipment rules. Every server placement goes through `place_player_body` in `players/spawning.rs`, and `PlayerMap` remembers retired generations so delayed snapshots and cues cannot revive them.

Observers play remote bodies through the shared `SampleBuffer` (`client/src/network/sample_buffer.rs`), `client.json::interpolation.buffer_intervals` update intervals behind the newest sample. Riders report carrier-local positions, resolved against the rendered carrier pose. Actors use the same buffer for `SActorMoves` and snapshots under one tick guard; remote players are fed by `SPlayerMoves` alone. Clients treat interpolated actors and remote players as stationary obstacles.

Characters configure an independent `movement_collider` (capsule) and `hitbox`; positions are feet-based. `common/src/physics/characters/support.rs` owns support queries, carrier selection, and ground following, and the final ground-support decision is documented at `finish_character_movement` in `characters/movement.rs`. Fall damage converts landing speed to an equivalent normal-gravity drop for the map's `player_fall` and `actor_fall` thresholds. Characters are not Rapier colliders: movement and projectile scans iterate the small player and actor lists with swept capsule tests (the comment at `character_paths_intersect` in `common/src/physics/characters/geometry.rs` explains the relative-segment query). Registering characters in the broad phase was weighed and rejected at these counts (movement ordering, self-exclusion, and a second collider set to keep in step on the client), as were Parry contact queries while every movement shape is an upright capsule.

#### Bullets

Every client simulates visible bullet flight, ricochets, portal crossings, and the character hit its own view detects; only the shooter reports character hits, reliably, while volleys ride unreliable cues. The shooter's muzzle check (`MuzzleCheck::Enforced` in `calculate_projectile_spawns`) decides the volley once and observers spawn it without repeating it. `client/src/input/weapons.rs` owns weapon selection and `input/shooting.rs` the cooldown. Shot delivery and in-flight lifecycle rules live in `common/src/protocol.rs`.

#### Missiles

Ammo comes from `missile_pack` items, capped by `missiles.max_missiles` (`pickup_has_effect` in `items/collection.rs` leaves a pack a full player cannot use). There is no cooldown, so ammo is the rate limit, and all launch feedback waits for the server's `SMissileLaunch` so a rejected shot never orphans a cue. The shooter owns the whole flight: lock-on (`client/src/missiles/lock.rs`), launch, guidance over `AirGraph` routes with a shared per-tick search budget (accounting documented in `missiles/search.rs`), the proximity fuse, and reliable reports of the detonation point and detected victims. The server applies the reported falloff with its own tuning (`common::physics::blast_hit` is the one falloff-and-shove rule), checks victim generations, resolves deaths and chain explosions, and detonates a missile whose owner stops reporting (`missiles/expiry.rs`). Missiles do not traverse portals; one that stops making progress self-detonates through the shared `ProgressWatchdog`. Ordering and lifecycle rules live in `common/src/protocol.rs`.

#### Portals

Q cycles the weapons the player owns (`client/src/input/weapons.rs` keeps the selected `WeaponMode` inside the loadout every frame, so fire, lock-on, and crosshair systems trust it). Login hands each player a portal slot (`PortalAssignments` and the authoritative `PortalMap` in `server/src/portals/resources.rs`): in `both` mode every slot owns a pair; in `single` mode adjacent slots share one. The firing client raycasts onto world geometry (`portal_surface_along_ray` owns what stops a shot), validates placement with `compute_portal_placement` (solid backing on one carrier, clear front space, per-face `portalable` permissions from the host map's texture catalog in `world/portal_backing.rs`, a Portal-2-style nudge when the fit fails; the whole aperture must fit one tile, so small cells never host one), and sends a carrier-local placement in `CPortalShot`. The server trusts that geometry while checking generation, assignment, equipment, cooldown, and shared overlaps (`server/src/portals/spawn.rs`), and keeps no `PortalSet`. A portal names its carrier and its `pos` and normal are in that carrier's frame, so the wire value stays constant while the carrier moves; the client re-places carried gates each tick (`carried_portals_refresh_system`). Overlap validation compares at the current tick only, so gates on different carriers may coincide later; nothing breaks. Portals ride `SSnapshot.portals`, with `SPortalOpened` as the placement cue and `SPortalFizzled` for rejected surfaces.

Traversal is true pass-through in `common/src/physics/portals/traversal.rs`, with placement and overlap validation beside it in `placement.rs`. While the owning client's body is in a linked aperture's front corridor, the movement step excludes the aperture's backing colliders; actors never fall through, and remote players use reported crossing boundaries. The carried-aperture rule and its reason sit at the top of `step_character_movement`. Only the owning client crosses a player (`client/src/portals/transit.rs`, camera mapping in `portals/view.rs`) and sends an immediate report; the repeated crossing marker makes observers cut between entrance and exit without acknowledgments, under the ordering rules in `common/src/protocol.rs`. The aperture frame derives from the surface normal alone, so ramps work unchanged; `portal_placement_yaw` and `PortalSet::funnel_displacement` keep hand-placed floor/ceiling fall loops alive.

Portal surfaces are off-axis render targets (`client/src/portals/render.rs`) rooted at the main camera, admitted largest on screen first under the one user-facing knob, `preferences.portal_view_budget` (0 disables see-through). Portal cameras render linear HDR with tonemapping off, so the presenting camera tonemaps once. A body straddling a gate is drawn on both sides through a hidden twin and `PortalClipMaterial` (`client/src/portals/clipping.rs`). The local player's meshes use a separate render layer, and camera-facing labels a main-view-only layer.

#### Ramps

Top-level `ramps` in the map JSON: `{lower_level, levels, cols, rows, direction, shape}` plus face materials — a footprint of cells, the storeys it rises, the side it rises toward, and `solid` or `plank`. Nothing reads the slope off the footprint: `map_core::geometry::ramp_error` checks the record and never the slope, so an over-steep ramp is valid and merely unclimbable (`CHARACTER_MAX_SLOPE`). `common/src/map/ramps.rs` derives the prism that both the collider and the mesh (`client/src/map/spawn/ramp_mesh.rs`) are built from, with face materials named by `Face::from_normal`. A ramp needs no floor under it: canonicalization (`enforce_ramp_floor_rules`) opens the floors and terrain of every level it passes, `terrain_excluded_cells` says why terrain differs under solid and plank ramps, and floor slabs end flush at its landings (`map_core::geometry::landing_edges`). Two ramps may share cells only where one ends on the level the other starts from, and other records stay off a ramp's footprint. A carried ramp neither pushes nor crushes (`carrier_contacts.rs`). The editor has one Ramp tool (`placement.py::add_ramp`), drawn on the ramp's lower level.

#### Ladders

Freestanding climbable elements anchored on a grid edge (`{lower_level, col, row, side, levels}`, top-level like ramps) — no wall or floor required, deliberately dumb (nothing inspects surrounding geometry), and one-sided: only the front is a ladder. Nothing rides the wire beyond `MapLayout.ladders`. The shared step derives climbing per tick from position and control intent against the front-only `LadderVolume`, a plain AABB with no Rapier collider; `clamp_move_at_ladder_plane` owns the fence rule. Actors opt in per kind through `actors.<kind>.can_use_ladders` (all shipped kinds are `false`); `LadderMode::for_actor` combines that with the actor's climb or exit intent, and routes carry explicit mount, climb, and exit actions with one actor per ladder.

#### Carriers

A carrier is a rigid group of map records that slides between two endpoints, and every carrier is a nested map. Its `motion` is `cycle` (out, pause, back, pause; an optional switch pauses and resumes it) or `follow_switch` (end 2 while on, end 1 while off). `common/src/map/carriers.rs` owns the tick-anchored `CarrierRun`, `carrier_offset_at`, and the `Carriers` runtime state; a switched run rides `SwitchState.carrier_runs`, and nothing per free carrier rides the wire, because both sides evaluate the same trajectory from the tick. The world is the implicit carrier 0; `MapLayout.carriers` lists the others, parents before children, and every layout record names its carrier and is expressed in that carrier's frame. Both sides run `carriers_advance_system` right before character movement; `CollisionWorld::set_carrier_poses` is the one place a collider ever moves. Riding happens inside `step_character_movement` (`supporting_carrier` in `characters/support.rs` owns the support rule); a body that leaves a carrier keeps its velocity as `AirborneMomentum`, while actors keep none. The client spawns one interpolated root entity per carrier (`client/src/carriers/`) and hangs every map entity under it; `map_level_visibility` is the one level-focus rule. Nothing keeps a carrier's path clear: `push_character_from_carriers` in `world/carrier_contacts.rs` resolves side contacts, and any crushing overlap that remains is fatal (`CharacterMovementResult.crushed`). Carriers are not Rapier kinematic bodies: those would add an integration step without replacing the riding, pushing, and crushing policies, and both sides already agree on carrier motion from the tick alone.

#### Nested maps

A map embeds named geometry in `nested_geometry`; a `nested_maps` entry `{map, level, from, to, to_level, travel_secs, pause_secs, phase_secs, from_nudge, to_nudge}` places one with its cell (0, 0) on parent cell `from` and slides it to `to`, and `from == to` on one storey is a room placed once. Nudges displace an end in wall widths and floor thicknesses (`carrier_from_motion` in `compile.rs`). Nesting is recursive and each nested map compiles as a carrier in its own frame (`definition/geometry.rs`, `definition/compile.rs`). `MapSource` in `map_core/src/schema.rs` holds the outer `MapDef` plus the named definitions; `map_core/src/load.rs` rejects missing references and cycles, unplaced definitions are scratch geometry that contributes nothing, and kinds resolve against the root's catalogs. Every setting comes from the map being played, and nested geometry may not define `switches`, `fields`, `fireworks`, or `nested_geometry`. Grid data is per carrier (`MapConfig.grids`): zones, items, and plates keep carrier-local cells; random items use the root grid alone. Nothing checks for overlap: outer slabs overlap the parent's wherever they touch, and a sliding map sweeps whatever lies along its path. The per-grid level-count limit is documented at `validate_map` in `map_core/src/diagnostics/validation.rs`.

A map's optional `settings.json::grounds` extends solid terrain around the root geometry at `level`, open to walk to the horizon; a player who walks off the far edge falls out of the world and the void rescue brings them back. `server/src/map/definition/grounds.rs` owns which geometry cuts the landscape (the root carrier's alone, never a nested map's), `common/src/map/ground_footprint.rs` the footprint rule, and `common/src/map/grounds.rs` the shared terrain and decorations, the same triangles for collision and rendering. Per-level `terrain` entries are complete accessible floor slabs with a procedural top and need no duplicate `floors` entries. The client side is `map/terrain/` (the shared cover field), `map/grass/` (deterministic streamed chunks; `client.json::grass` exposes only `enabled` and `color`), `map/trees.rs`, and `map/rocks.rs` (shapes from `common/src/map/rocks.rs`, so physics builds one hull per class and variant); pebbles are never solid, and every tree, stone, and boulder is.

#### Weather & celestial lighting

Every map uses the same procedural HDR sky. `celestial` (a `gameplay.json` default a map may override) supplies latitude, season, north yaw, start time, and a normalized moon phase; north is world +Z, east +X. `common/src/celestial.rs` owns the solar and lunar model and `CelestialClockAnchor`, which `SInit` and every snapshot carry; clients extrapolate against `ServerTick`, so motion is frame-smooth at any snapshot rate. `/time` and `/moon` control it. `client/src/materials/sky.wgsl` renders the sky on a camera-private sphere shared by the main and portal cameras; `map/clouds.rs` mirrors the cloud layer on the CPU so a cloud crossing the sun dims the light, and `map/sky_probe.rs` feeds ambient and reflections (the comment on `SkyProbe` says why it crossfades). `SkyState`, derived once per frame by `celestial_state_system`, drives the sky material, both directional lights, ambient, grading, and fog. The deferred renderer is the shipped `rendering.opaque_renderer`; the buffer-packing constraint is documented beside `ProceduralSkyMaterial` in `client/src/materials/sky.rs`. `client.json::sky` and `lighting` hold the art-directed values; stable palette values live in `client/src/constants.rs`.

Weather is independent: a map's concrete or `auto` mode seeds `weather_system`, `cloud_cover` and `raining` ride each `SSnapshot`, and the client smooths and renders them (`vfx/rain.rs`, `map/weather_surfaces.rs`). `/weather` reports or holds it.

#### Actor lifecycle

`actors_removal_system` routes health-zero deaths and crushes through `kill_actor`; lethal landings go through it from `actors_fall_damage_system` with no kill credit, and a ground actor that falls out of the world despawns silently. `actors_respawn_system` refills each vacated slot on its own countdown of the zone's `respawn_secs` (`null` never refills). `ActorSpawnZone::is_enabled` is the one gate: a zone spawns only while it is on, and the switch never touches a countdown. A zone with `until_checkpoint` spawns only while the live `checkpoint_progress` is short of it; `on_checkpoint` is `stop` (default) or `destroy`, which also self-destructs the zone's actors without credit (`zone_course` in `map_core/src/diagnostics/records.rs` validates both). The map's `respawn.actors.on_player_death` selects the shared death trigger and `scope` selects `dead` or `all` (`reset_actors` in `actors/spawning.rs`). Replacements queue in `PendingActorSpawns` with ids, spots, and headings reserved and materialize after the zone's `beam_in_secs`; both sides read the shared tick against a `SpawningActor`'s reserved and due ticks, so the ghost's fade is a pure function of it.

Spawn-zone `count` is a nonempty, nondecreasing list: the targets for one, two, three, and four-or-more logged-in players (`ActorSpawnZone::target_count`; dead players count, an empty server uses the first entry). The fill tops each zone up to its target every tick, so a join spawns only its new slots and a rejoin never revives a permanent kill. Zones span `levels` storeys from `level`, with the count applied once to the whole volume. Immovable actors spawn at unobstructed cell centres, flying actors sample clear air and recheck before materializing, and movable actors keep random placement. A fill with no free spot retries every tick and warns once per blockage: a crowded zone is a map design problem, not a rule.

#### Actor AI

All movable ground actors use surface navigation. Goal decisions run at 10 Hz; route execution, physics, beam targeting and damage, and timers run every server tick. Anchored actors check for exposed beam targets every tick without navigation state, and flying actors keep incremental 3D navigation without gravity.

Each spawn zone owns `roam_distance` in metres (default 0), measured from the authored spawn volume (`server::map::ZoneVolume`). Pursuit and evasion may leave the home; ground actors return to the actual spawn volume, not the roaming extension, before roaming again after a chase, evasion, or `/peace`, and a blocked home stays the goal and is retried (`behavior/home.rs`). Ground routes use carrier-local positions and revisions, with automatic ladders and parent-carrier docks; missing support and stalls lead to waiting or failure and replanning, never to random escapes.

Threats are acquired by line of sight within spherical vision and remembered for the kind's `threat_memory_secs`, in the carrier frame they were seen in. Ground actors pursue reachable targets at the nearest point their body can occupy (`SurfaceNavigation::pursuit_goal` says why); `behavior/pursuit.rs` projects airborne targets onto the surface beneath them and keeps the previous goal over gaps. An unreachable supported threat sends an armed map's actors to cover or distance; when `PlayerMap::players_can_be_armed` is false, unreachable players are ignored. `behavior/beam.rs` shares beam timers and retargeting, and `behavior/geometry.rs` cover and attack checks.

`/peace [on|off]` toggles `ActorMap.peaceful`: actors forget targets and stop attacking, including contact detonation, and `SSnapshot.actors_peaceful` clears beam effects on clients. The startup flags `--god` and `--peace` initialize `Invincibility` and `ActorMap.peaceful` in every mode.

### Conventions

- Do not include the user's real name in repository content.
- This is pre-release software: JSON configs, map files, and the wire protocol are intentionally unversioned, and breaking changes are allowed. Update every producer, consumer, fixture, and checked-in config together; do not add version fields, compatibility branches, or migrations unless this policy changes. The one exception is the gitignored `config/client/client_local.json`, which git cannot update — see its entry above.
- JSON uses `[]` for empty lists, `{}` for empty dictionaries, and `null` for absent single values; an empty object does not disable a configuration block. Omitted fields use documented defaults or are inapplicable to the selected variant. `grounds`, `random_items`, `placed_items`, and root-layout `fireworks` require an object or explicit `null`; the first three are map content with no default. Required nullable fields use `common::config::deserialize_required_option`; its comment explains the Serde constraint. Nested-map `to_level` omitted or `null` inherits `level`, and the editor writes the resolved number. Collection fields never use `null`.
- Entity IDs are newtype wrappers: `PlayerId(u32)`, `ActorId(u32)`, `ItemId(u32)`, `MissileId(u32)`, `FieldId(u16)`.
- Bevy resources `PlayerMap` / `ActorMap` / `ItemMap` / `MissileMap` map IDs to entities on both sides.
- Shared player/actor behavior belongs in `characters` and is named accordingly. Portal systems own portal behavior; general movement and gameplay effects must run without portal traversal.
- Living local players are repositioned only when a spawn or explicit relocation establishes a new body generation; a dead local body stops stepping where it died. Remote players, actors, and observed missiles play buffered samples through the one `SampleBuffer`, without physics or reconciliation. Missiles simulate only on their shooter.
- Crossbeam channels carry decoded `ClientMessage`/`ServerMessage` values: every sender holds a shared handle, and one system per frame hands the batch to renet, so gameplay code never touches the transport and the server's broadcasts do not know which players are remote. Receiving from a remote link is direct. The host's own client holds the other ends of its embedded server's queues, so nothing is serialized or forwarded in-process. A closed queue is the disconnect in both directions. There is no async runtime.
- Coordinates: Bevy Y-up `(x, y, z)`, units in meters.
- Wire format: `bincode` 2 (binary).
- Network reviews must follow the **Self-repairing state: an intentional trade-off** contract in the [protocol header](common/src/protocol.rs). Read its accepted-consistency model and criteria for defects before proposing ordering or acknowledgement machinery; temporary inconsistencies alone are accepted behavior.
- `score` (server `PlayerInfo.session.score`, client `PlayerInfo.score`, wire `Player.score`) accumulates per-event deltas from the server config's `scoring` block and persists across deaths. Don't confuse with `health`.
- "Dead": on the server, `PlayerInfo::is_dead()` means its per-life lifecycle is `Dead` (an individual timer) or `GroupRespawn` (the timer lives on `PlayerMap`), neither of which owns an entity. On the client, `LocalPlayerInfo.is_dead` is a separate flag. Don't try to unify the two — they live in different crates.
- Keep gameplay concepts (`Wall`, `Floor`, `Ramp`, `Barrier`, items, spawn zones) in map/protocol types; keep movement/collision behaviour both crates run in `common::physics`; code only one crate runs lives in that crate.
- Mesh UVs are computed from the record's position in its carrier's frame (world position on the world carrier), not from the mesh's local position. Floor/wall/ramp builders in `client/src/map/spawn/` take `carrier_center` (and `rotation` for walls); each vertex's UV is `(carrier_center + rotation * local_pos) · uv_axis / tile_size`. New mesh builders should follow the same pattern; a carried mesh's frame moves with it, so its texture never swims.

## Map editor (`tools/editor.py`)

The editor requires Rust/Cargo, Python 3.10 or newer, and PySide6. `python3 tools/editor.py <map>` checks and builds the native adapter automatically; `cargo build --release -p map_core_py` can warm the build beforehand. Only maps registered in `config/server/gameplay.json` can be opened. Python retains widgets, selection, document transactions, autosave, and undo. The Python geometry, normalization, validation, nesting, and transform modules are adapters to `map_core`; add map rules there rather than another Python implementation.

The canvas IS the UI. Do not add coordinate readouts, row/col numbers, or status-bar grid info — if something needs explaining, it should be drawn on the canvas itself. Feedback is a temporary canvas notice, tool properties sit in the toolbar and placement reuses them, and Tools and Properties stay visible with no close or toggle controls.

Rules that hold across the editor:

- The editor never writes `settings.json`. It reads textures and drawing geometry from the map's effective settings (`load_map_settings` merges the `gameplay.json` defaults with the map file through `map_core`) and watches both files; `catalogs.py` holds every loader, and `MapCatalogs` is the one value a window adopts for a map. It also reads `config/client/assets.json` (wall-light kinds) and `client/assets/symbols/items.json` (item glyphs); texture images are neither read nor watched.
- `MapDocument` owns edit transactions and undo history. Save, autosave, and undo cover the whole parent document, including named nested geometry (the Map selector switches between them) and catalog edits.
- `editing.py`, `erasing.py` (with the `ERASE_GROUPS` table behind every `Erase <group>` tool), `regions.py`, `transforms.py`, and `nesting.py` hold widget-free map operations that import no Qt, and every operation works in grid units (`viewport.py` converts once, at the canvas; edge picks share `EDGE_PICK_PIXELS`).
- Loading keeps invalid records; `repairs.py` proposes explicit undoable repairs, and Map → Check Map lists issues across the outer map and every nested definition. Validation warnings never block an edit, a save, or a load.
- There is one selection: `selection.py` defines the immutable value (explicit object references or a tile area, with a paste anchor) and `selection_state.py` publishes it to Properties, highlights, handles, connections, and every command. `interaction.py` owns the one active mouse gesture and resolves targets identically for left and right clicks. Changing tool, level, geometry, selection scope, or the level count clears the selection.
- Properties has no Apply step: `SelectionProperties.commit` owns when a field commits, how a failing draft waits, and how one selection visit merges into one undo entry (`SetMapCommand`'s `merge_key`). Shortcuts are scoped to the canvas so editing text cannot edit the map.
- Placement never deletes a ladder or moves an existing nested-map end. Deleting, cutting, or moving a floor or wall takes the items, plates, and lights it held (`with_supported`), and validation refuses edits that would remove any other unselected dependent. In-use fields and switches cannot be deleted, and renames update references throughout the document.
- Checkpoint numbers are whole numbers from 0 and may repeat freely: nothing refuses or renumbers a duplicate, so copies, transforms, and generated nested definitions keep their numbers. Number 0 is the start (`START_CHECKPOINT` in `constants.py`), always saved as `individual`, and a new map seeds one (`started_map`). Edit Checkpoints renumbers as one undo entry, with every zone's `until_checkpoint` following (`checkpoint_numbers.py`).
- Actor spawn zones have no ground-support or floor-capacity checks; surface suitability belongs to the map designer. Zones stay one object across their level span.
- Edit Levels and Resize Map stage their changes until OK and apply as one undo entry; `map_core/src/transforms/operations.rs::edit_levels` derives geometry from the final rows, and the shared core behind `transforms.py::map_content_bounds` covers every record family and nested footprints at both motion ends.

Where things live in `tools/map_editor/`:

## Adding a texture

Texture sets are freepbr.com UE packs. Follow this workflow for every added pack, including model-generation sources. Catalog entries are metadata; load texture images only when a material is used.

Use a distinct model texture only when it contributes visibly at normal gameplay distance; reuse an existing material for tiny details. Generated models share catalog PBR loading and metre-scaled UVs in `client/assets/models/modelkit/materials.py`. Each model has a matching `.json` beside its GLB for material tuning; rebuild the GLB after changing it (controls and commands in `client/assets/models/MATERIALS.md`).

1. Prepare the pack outside `client/assets`; keep only used texture maps in `client/assets/textures/<name>-ue/`, resized to 2048² like every shipped pack. Textures embedded in active models and inputs needed to regenerate them count as used; unused variants, height maps, and previews do not.
2. Build the packed metallic-roughness map Bevy wants (needs ImageMagick): `client/assets/textures/combine_metallic_roughness.sh <dir>/<name>_roughness.png <dir>/<name>_metallic.png` writes `<name>_metallic-roughness.png` next to them. `multiply_intensity.sh <metallic-roughness.png> [roughness_add] [metallic_multiply]` retunes it afterwards (keeps a `.original.png`).
3. Copy the required maps, including the packed metallic-roughness map, into the asset directory. Add a `materials.<name>` entry in `config/client/assets.json`: `textures.base_color` (`_albedo`), `normal` (`_normal-dx`; the name must carry `-normal-dx` or `-normal-gl`, since the client flips DirectX maps and both loaders reject an unsuffixed name), `occlusion` (`_ao`), `metallic_roughness`; `tile_size` in meters; `repeat` and `linear_data_textures` true. Use a neutral white occlusion image when a pack has no AO map.
4. Name the material from an alias in the `settings.json::textures` of each map that uses it, with an explicit `portalable` boolean (`{ "material": "<name>", "portalable": true }`). Map faces use those aliases, and no map may define `terrain`, the procedural terrain's alias; the ladder, rock, and terrain bindings in `assets.json` name their texture sets directly. Pressure plates use the materials embedded in their GLB.
5. Compare the four catalog paths with the directory listing character by character: macOS opens a wrong-case path that Linux cannot. `cargo test --release -p client assets` validates the entry itself (normal-map suffix, footstep binding), not the files.

## Coding style

- Rust edition 2024. Format with `cargo fmt` (see `rustfmt.toml`).
- Repeated dependency versions and the shared `common` crate path live in the root `Cargo.toml` under `[workspace.dependencies]`; members inherit them with `workspace = true`. Keep member-specific features in their manifests. Bevy defaults are disabled at workspace level and explicitly enabled by the client; preserve that distinction when updating dependencies.
- Workspace lints (root `Cargo.toml`): `unsafe_code = "forbid"`; `unwrap_used = "warn"` — prefer `expect("…")` with a message, or proper error handling; `todo = "warn"`.
- Naming: `snake_case` functions/modules, `CamelCase` types, `SCREAMING_SNAKE_CASE` constants.
- Reserve `constants.rs` for appearance, gameplay, and performance tuning; keep implementation details beside their owning code, with shared definitions where consumers must agree.
- In `constants.rs` files, constants that logically belong together share a descriptive prefix and stay grouped together (for example, `MISSILE_EXHAUST_*` and `EXPLOSION_*`). Constants defined in other files are exempt from this grouping and prefix rule.
- Imports are nested `use` trees wherever possible (one `use` per crate root, paths grouped in braces); no `use ... as` renames unless a name collision leaves no alternative.
- Do not introduce `Arc` just to make borrowing or ownership convenient. Reserve it for genuine cross-thread shared ownership or APIs that require it; otherwise prefer references, owned values, IDs/indices, or restructuring ownership.
- Use `assert!` / `assert_eq!` / `assert_ne!` for invariants — never `debug_assert!`. Only release builds run, so `debug_assert!` is a no-op.
- `mod.rs` files contain only `mod` declarations and `pub use` re-exports (attributes like `#[cfg(test)]` on them are fine) — no functions, types, or impls. Code that would land in a `mod.rs` goes in a named sibling file (e.g. `plugin.rs`) and gets re-exported.
- A module with submodules uses `<module_name>/mod.rs`; never pair `<module_name>.rs` with a sibling `<module_name>/` directory.
- Default to writing no comments. Only add one when the WHY is non-obvious: a hidden constraint, a subtle invariant, a workaround. Don't explain WHAT well-named code already says.
- When a code comment is the authoritative description of a rule or invariant, point to it from `AGENTS.md` instead of duplicating it; keep one source of truth.

## Testing

Add tests selectively for algorithms, state transitions, interactions, persistence, and meaningful regressions. A code change does not automatically need a new test. Do not test cosmetic tuning, trivial getters, duplicated constants, or restatements of the implementation. Remove redundant coverage while preserving distinct failure scenarios. When a test breaks, decide whether it caught a bug, needs simpler setup, or should be removed before updating expectations.

A shared fixture may load a shipped configuration file as the base of a whole-schema value (`ClientSettings`, the server's `GameplayFile`); every test pins the values its assertions depend on, so a tuning change never moves a test's expectations. Whatever can be small stays test-owned: the test map, the asset catalog, and the JSON that loader and serialization tests write to temporary files. Shared fixtures return fresh values. Do not copy a shipped file into a fixture, or add production defaults just for tests. Editor fixtures install their catalogs before constructing windows or documents, including file watchers and command-line entry points.

`cargo test --release --workspace` is the canonical command. Unit tests live
in a `tests/` directory beside the module they cover, one file per source
file: the tests for `physics/abs.rs` are `physics/tests/abs.rs`, declared at
the end of `abs.rs` with `#[cfg(test)] #[path = "tests/abs.rs"] mod tests;`,
so `super` is the module under test and private items stay reachable. Tests
that cover a whole directory module are declared from its `mod.rs` the same
way (`tests/<name>.rs`, module `<name>_tests`) or as that directory's
`tests.rs`/`tests/mod.rs`; `include_str!` paths in a test count from the
`tests/` directory. Shared fixtures live under `tests/` beside the code they serve and keep
their module names through `#[path]`: `common/src/tests/geometry.rs` and
`server/src/tests/geometry.rs` (`test_geometry`), `client/src/tests/fixtures.rs`
with its JSON in `client/src/tests/fixtures/` (`test_fixtures`), and
`server/src/config/tests/fixtures.rs` (`config::fixtures`). No source
file holds an inline `mod tests`, and there are no crate-level `tests/`
integration-test directories. Name tests after what they assert
(e.g. `lethal_hit_returns_true`, `matching_keys_open_all_barriers_of_their_kind`).
The map editor's headless `unittest` suite lives in `tools/tests/` and covers
its pure geometry, normalization, resizing, validation, document transactions, and canvas interactions. `test_editor_input.py` exercises mouse and keyboard events through the shared input controller, including matching left/right selection, handle resizing, object moves, cancellation, and text-field shortcut isolation.

Shipped models may be loaded for compatibility checks using an explicit
test-owned model catalog. Assert only runtime requirements (rig node names,
clip indices, the emissive/housing split, texture colour spaces), never
incidental material or texture counts or unrelated bone names. Do not read
`config/client/assets.json` to configure these tests.
`client/src/tests/assets.rs` (module `test_assets`) is the headless app
every such test loads through: spawn models with `load_character_model`, preload bare GLBs with
`preload_gltfs`, then `settle` before sampling; it fails a test whose scene
was spawned twice.

## Documentation

- `README.md` is for players: a high-level description of what the game is, how to run it, and the controls. Keep it at that altitude: no rules, mechanics, config paths, editor workflows, or version numbers, and no line per feature. Do not update it for every change; a code change rarely touches it, and it must not turn into a technical spec sheet or a changelog. Feature detail belongs here in `AGENTS.md`.
- `AGENTS.md` is for developers and agents, and every session loads all of it, so it holds only what reading the code cannot supply: settled decisions and rejected alternatives, invariants that span crates, conventions, workflows, the config semantics a map author sees, and a map of where things live. A module entry is its role and a pointer to the comment that owns each non-obvious rule; mechanisms, tuning numbers, and step-by-step behaviour belong in code comments, never restated here. Write at the depth of the sibling entries.

## Commits & pull requests

- Whenever the repository has uncommitted changes, include a suggested commit message in the final response covering the entire outstanding change set, including work from earlier turns and user edits. Check staged, unstaged, and untracked changes; never assume earlier work was committed.
- Short, imperative summaries.
- PRs: describe behaviour impact on client/server, include repro steps or screenshots for client-facing changes, call out protocol or asset changes explicitly (they're breaking by default).

## Security & assets

- **Current threat model:** development and private/LAN play assume cooperative clients. Abuse hardening — client rate limits, per-tick ingress budgets, bounded/backpressured network queues, flood protection, and admin authorization — is intentionally deferred. Revisit it before any public release or publicly accessible server.
- `client/assets/` are not open source — replace before publishing a fork.
- netcode runs in unsecure mode: sessions are encrypted with the zero key, so anyone who can reach the port can join. Fine for LAN play; revisit with the hardening above.
